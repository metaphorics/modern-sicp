# Exercise 2.76 — adding types versus operations (adapt)

The map class is `A`: this edition compares OCaml's own three ways
to organize the same generic system instead of Scheme's three named
styles, since two of the three (explicit dispatch and message
passing) map onto OCaml constructs almost unchanged and the third
(data-directed) already has a main-text worked example (`Sec_2_4`)
to point back to. `ex_2_76` builds a rectangular `(3, 4)` and a polar
`(5, 0)` complex number three ways and checks `real_part` and
`magnitude` agree across all three, so the comparison below is about
working code, not three unrelated sketches.

**Adding a new representation.** With explicit dispatch
(`explicit_z`, a closed variant matched by `real_part_explicit` and
`magnitude_explicit`), a third representation means adding a
constructor to `explicit_z` and a case to every one of its match
statements — the compiler forces every site to update, which is
exactly the point of a closed variant, but it does mean every
existing generic operation's source changes. With data-directed
dispatch (`dd_table`, `dd_install_rectangular`, `dd_install_polar`),
a third representation means one new `dd_install_*` function calling
`Hashtbl.replace`; `dd_apply_generic` never changes, because it never
named `"rectangular"` or `"polar"` anywhere in its own source — only
the installers did. With message passing (`mp_rectangular`,
`mp_polar`), a third representation is one new function returning an
`mp_op -> float` closure; nothing else changes, for the same reason.
Data-directed and message-passing are additive here; explicit
dispatch is not.

**Adding a new operation.** With explicit dispatch, adding `angle`
means one new function with one `match` arm per existing
representation — contained, and the compiler's exhaustiveness check
means a forgotten representation is a compile error, not a silent
gap. With data-directed dispatch, adding `angle` means calling
`Hashtbl.replace table ("angle", tag) ...` once per existing
representation, inside each representation's own `dd_install_*`
function — so *that* function must be revisited for every
representation, the same count of edits as the closed-variant case,
just spread across different functions instead of gathered into one.
With message passing, adding `angle` means editing every
representation's dispatch closure (`mp_rectangular`, `mp_polar`) to
add an `Angle` arm — again one edit per representation, and unlike
the table case, a forgotten representation is a compile error here
too, since `mp_op`'s pattern match must stay exhaustive.

**Which organization for which system.** A system where new
*representations* arrive often (new complex-number packages, new
kinds of records) wants data-directed or message-passing dispatch:
adding one costs one new, self-contained unit of code, and nothing
already installed is touched. A system where new *operations* arrive
often wants explicit dispatch: adding one costs one new function
gathering every representation's case in one place, where a missed
case is visible in one review, rather than one small edit scattered
into every representation's own file. Message passing shares
explicit dispatch's exhaustiveness check for new operations but pays
for it with the same scattering data-directed dispatch has for new
representations — of the three, it does not have a "free" side the
way the other two each do.
