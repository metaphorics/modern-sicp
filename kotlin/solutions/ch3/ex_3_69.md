# Exercise 3.69: triples and the Pythagorean stream

## Approach

`triples` conses the diagonal triple per level, then interleaves the
first component mapped over `pairs(t.tail, u.tail)` with the `triples`
of the tails; the pairs already guarantee `j <= k`, and the level
structure guarantees `i < j`, so the stream is exactly the non-decreasing
triples (prefix starts (1, 1, 1), (1, 2, 2), (2, 2, 2), (1, 2, 3),
(2, 3, 3), all obeying `i <= j <= k`). `pythagoreanTriples` filters that
with `i^2 + j^2 = k^2`. The first six in stream order are (3, 4, 5),
(6, 8, 10), (5, 12, 13), (9, 12, 15), (8, 15, 17), (12, 16, 20); the
test pins the first four, because the sixth sits about 293k elements
into the interleave and walking that far retains a memoized graph the
shared test JVM cannot hold.

Independent check: a python3 simulation of the same interleave law
enumerated the triples and produced the same six values in the same
order (at triples-stream indices 18, 606, 6126, 14078, 81790, 292862),
and an independent brute-force enumeration of all Pythagorean triples
with small legs contains exactly those values in that order.

## Map class

`T` (map row 3.69: the triples exercise translated to Kotlin's memoized
streams as written; the map's coprimality note is a separate variant not
required by the statement).

## Deviation

The miss-skipping filter is a cursor loop rather than the recursive
`streamFilter` shape: Kotlin has no tail calls, so the recursive form
spends one JVM frame per miss, and the run of misses before the sixth
triple is about 211,000 long, which overflows the stack. Each hit is
still a delayed `consStream`, so the stream stays lazy between hits.
