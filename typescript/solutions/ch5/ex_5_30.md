# Exercise 5.30: error signaling inside the evaluator

Both parts are built, and the places that needed the change are the two the exercise names.

(a) `lookup-variable-value` answers a distinguished condition code for an unbound variable, a tagged word carrying the reserved `condition` tag and the detail message, which no user value can spell: the word predicates exclude it from `variable?` and the renderer prints only its detail. `ev-variable` tests the code with a new `condition?` operation and goes to `signal-error` instead of using `val`.

(b) `apply-primitive-procedure` keeps every applicability check the primitives already make, a wrong operand count, `car` of a non-pair, division by zero, but a failed check surfaces as the condition code instead of escaping the machine, and `primitive-apply` tests for it, cleans the stack the way `unknown-procedure-type` does with `(restore continue)`, and goes to `signal-error`. The base controller's `signal-error` is the book's arrangement: `user-print` reports the condition's detail and the jump back to `read-eval-print-loop` leaves a stack the next interaction's `initialize-stack` cleans.

The caught failures are pinned by their printed detail: `(/ 1 0)` answers `division by zero`, `(car 5)` answers `type error: car`, the unbound variable answers `unbound variable: no-such-variable`, `(cons 1)` answers `arity mismatch`, and `(5 6)` reports `unknown-procedure-type-error`, each printed by the machine and followed by a return to the driver loop rather than a stop. A clean factorial still answers `120`, so the checks did not change correct answers.
