# Exercise 1.22 — timed prime search (adapt: Sys.time replaces runtime)

The map class is `A`: `Sys.time` stands in for the book's `runtime`
primitive, returning seconds as a `float` instead of microseconds as an
integer, and the honest answer to "do your timing data bear this out"
changes with the clock.

`search_for_primes start count` walks every integer upward from
`start`, testing each with `is_prime`, collecting the first
`count` that pass. `ex_1_22 ()` runs this for the four thresholds and
finds `[1009; 1013; 1019]`, `[10007; 10009; 10037]`,
`[100003; 100019; 100043]`, `[1000003; 1000033; 1000037]`, matching the
book's expected primes exactly.

**On timing.** A modern CPU tests a four- or five-digit number for
primality in well under a microsecond; `Sys.time`'s resolution (often
around 10 milliseconds on common platforms) cannot see a single call at
all, so `timed_prime_test` on any of these twelve primes usually reports
`Some 0.0`. The `Theta(sqrt n)` prediction — that primes near 10,000
should take about `sqrt 10` times as long as primes near 1,000 — is real,
but confirming it honestly needs each test run many times in a tight
loop and the total divided by the count, not a single call read off the
clock; a single-call timing that shows `0.0` at every threshold is not a
failure of the algorithm; it is the clock's resolution winning. The test
here checks only that `timed_prime_test` correctly returns `None` for a
composite and a nonnegative `Some` for a prime, which holds regardless
of resolution.
