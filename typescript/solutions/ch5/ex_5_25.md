# Exercise 5.25: normal-order evaluation in the controller

Thunks are machine words, the tagged `thunk` word of an expression and an environment, built by one operation, `make-thunk`, so the base word set carries the laziness. Thunked operands bind through the unmodified environment: the parameter is bound to the thunk word itself, which `lookup-variable-value` answers like any bound value.

The controller changes in exactly three regions. The argument loop thunks every operand and adjoins it with no saves and no recursion, which is the laziness. `ev-variable` forces a thunked binding the first time the variable is read, evaluating the thunk expression in the thunk's environment, and memoizes by storing the forced value over the binding with `set-variable-value!`. `primitive-apply` forces any thunks left in `argl` before the primitive sees them, saving `proc`, `argl`, `unev`, and `continue` around each nested evaluation, one thunk per pass, and memoizing into the thunk word in place; the override of `apply-primitive-procedure` unwraps forced thunks so the primitive only ever sees values.

One deviation is recorded: memoization is per binding, not per thunk object. A thunk aliased into two variables recomputes; every session here observes single-variable references, where the two agree.

The tests exercise the memoized delay where strict order fails: `(test-order 0 (p))` answers `0`, the chapter 1.5 program that diverges under strict evaluation; `(always-42 (car (quote ())))` answers `42` although the unused argument would fault if evaluated; `(use-twice (bump))` answers `(1 . 1)` with `count` left at `1`, so the thunked `(bump)` ran once, not once per reference; and `(factorial 5)` still answers `120`.
