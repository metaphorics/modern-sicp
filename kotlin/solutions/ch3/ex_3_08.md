// Chapter 3, exercise 3.8 rationale

## Exercise 3.8: expose operand evaluation order

Approach: `makeF` closes over one `var firstCall`, true until the first
call anyone makes to the returned function. That first call returns its
own argument; every later call returns 0. In `f(0) + f(1)`, `+` desugars
to `a.plus(b)`, whose receiver `a` (`f(0)`) is evaluated before its
argument `b` (`f(1)`), a guarantee of the Kotlin language, not an
accident of one compiler, so `f(0)` is the first call and keeps its
argument 0, while `f(1)` is the second call and answers 0 as well: the
sum is always 0. Writing the same function calls in the other order,
`f(1) + f(0)`, makes `f(1)` the first call instead, and the sum becomes 1.

Class: corrected from the map's `T` to `A: order defined; exercise
verifies it`, matching the note already recorded for Rust and TypeScript
on this row. SICP's original exercise exploits an interpreter's
unspecified operand order; Kotlin has no such freedom to expose, so the
exercise becomes a proof of the guarantee instead of a search for an
accident. Deviation: the statement is adapted (D30's `A` class); the
construction of `f` itself is unchanged from the book's own hint.
