# Exercise 3.63: sqrt-stream memoization locality

## Approach

The exercise is answered by measurement. Both structures are built with an
`Rc<Cell<u32>>` meter in place of the bare `sqrt-improve` step: the shared
version is the module's `sqrt_stream` translated one-for-one (one
self-referential definition whose tail maps over the named stream), and
Louis's version conses the seed onto a map whose source is a fresh recursive
call, so every level of the tower is a brand-new stream. A walk of the first
`k` elements costs `k` improve calls on the shared spine -- each advance
forces one more tail, and each forced tail's map head is one improve of the
previous guess -- and `k(k+1)/2` calls on Louis's tower, because producing the
`k`-th element re-derives a `k`-level tower from the seed. Five elements cost
(5, 15); six cost (6, 21); both metered twins are checked element-for-element
against the module's `sqrt_stream` so the meter is the only difference. The
second half of the question: if `delay` were the unmemoized
`(lambda (exp) (lambda () exp))`, the shared version would degenerate into
Louis's -- each access would re-derive its predecessors -- and the measured
contrast would collapse; the local `guesses` binding only helps because the
memoized `delay` makes the one spine reusable.

## Map class

`T`. The statement translates whole; the Rust wrinkle is that the meter rides
in the mapping closure, and the counts are pinned from runs rather than
asserted from theory.

## Deviation

None of substance. The counts include the walk's own advance (one tail force
per element), which is stated in the test comments so the pinned numbers are
reproducible from the stated walk.
