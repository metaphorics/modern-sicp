# Exercise 4.15: halts?, answered with a step budget

## Approach

The book asks for `halts?`, a procedure deciding whether its argument
terminates, and supplies the diagonal: `(try try)`, where `try` runs
forever exactly when `halts?` says it halts. A decider cannot exist
because a correct `halts?` would have to disagree with itself on that
input. This host states the impossibility operationally instead of
hanging: `Bounded` counts one step per `step` round (the extension
seam, so operator and operand evaluations and every body hop are
counted) and a run that outlives its budget dies with the typed
`MachineFault` ("step budget exhausted after N steps"), the evaluator's
own resource fault rather than a program-level error. `halts?` is
installed as a primitive the host controls, a stub whose canned answer
the caller flips; the book's dialogue
(`(define (run-forever) (run-forever))`,
`(define (try p) (if (halts? p p) (run-forever) 'halts))`,
`(try try)`) then demonstrates the diagonal honestly in both
directions: the stub that answers `#f` watches the program halt anyway,
and the stub that answers `#t` watches it run on anyway. Either canned
answer is wrong about this input; the budget is the witness that the
`#t` run provably does not terminate, in place of an infinite loop the
test suite could not survive.

## Map class

`T`.

## Deviation

None. The book's hypothetical `halts?` is realized as the stub-plus-
budget pairing the reworded statement asks for; nothing claims to decide
halting.

## Answer

- With `halts?` answering `#f`: `(try try)` takes the `'halts` branch
  and the run terminates printing `halts` (transcript `"halts\n"`),
  a program the stub swore would not halt.
- With `halts?` answering `#t`: the `'run-forever` branch spins until
  the budget fires (transcript
  `"Error: machine fault: step budget exhausted after 1000 steps\n"`),
  a program the stub swore would halt and provably did not.
