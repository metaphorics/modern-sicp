## Exercise 2.74: division records

Approach: `DivisionFile` is a sealed hierarchy with one variant per
division's genuinely different storage shape (North keeps a map of name
to field map, South keeps a flat property list per employee), and
`getRecord` dispatches on that hierarchy, tagging every hit with a
`TaggedRecord` so `getSalary` never needs to know which division a
record came from.

Part (a): `getRecord` is applicable to any `DivisionFile`; the type
information every division's file must supply is exactly the sealed
variant it constructs itself as.

Part (b): `getSalary` reads the `fields` map on a `TaggedRecord`
uniformly, because `getRecord` already normalized North's nested map and
South's flat property list into the same field-map shape before tagging.

Part (c): `findEmployeeRecord` tries every file's `getRecord` in turn and
returns the first hit.

Part (d): a new division needs one new `DivisionFile` variant and one new
`when` arm in `getRecord`; North's and South's own lookup code, and
`getSalary` and `findEmployeeRecord`, need no changes at all.

Class: A, per the map; the idea survives (dispatch on a division tag,
normalize into a uniform record), but the statement changes because a
sealed hierarchy needs an explicit variant and `when` arm per division
rather than the book's fully open runtime tag: adding a division is one
new case, not zero, which is the map's "per-division adapters" note.

Deviation: none in substance.
