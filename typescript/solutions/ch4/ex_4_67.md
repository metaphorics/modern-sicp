# Exercise 4.67: a loop detector

## Approach

The exercise asks for a design, with engine surgery as follow-up, so
the solution is the design as tested host code: `LoopDetector`
histories rendered atomic patterns along the live deduction chain.
Re-entering an equivalent pattern is refused; completing a
derivation releases it. Frames stay out of the key — the same
pattern under different bindings is legitimate progress, and only
the pattern cycle (4.64's unconstrained middle-manager reopening
itself) is cut.

## Numbers

The tests pin the mechanism on real 4.64 queries: double entry
refuses, release re-admits, distinct patterns coexist. No engine
integration is claimed — the detector is exercised standalone, and
the report records engine integration as follow-up work.

## Class and deviations

Translated row. Deviation: design-as-code rather than engine
modification, which the exercise explicitly permits ("you may want
to modify the system" only after studying the implementation). The
history key (relation plus rendered pattern, variables included) is
the lesson's load-bearing choice.
