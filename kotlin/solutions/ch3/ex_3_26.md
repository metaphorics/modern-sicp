// Chapter 3, exercise 3.26 rationale

## Exercise 3.26: the table as a binary tree

Approach: the records hang off one `root: TreeNode?` instead of an
unordered backbone. A `TreeNode` is a (key, value) record with `left`
and `right` slots, mutable in place like every record of this section:
`lookup` walks one root-to-leaf path, comparing keys and following the
smaller/larger branch, and answers the value at an exact match or null
at a null leaf; `insert` walks the same path, overwrites the value of
the node it matches, and hangs a fresh node on the null slot where the
walk falls off. Nothing is ever scanned linearly; the number of
comparisons is the depth of the tree, which is the book's reason for
preferring this shape for large tables.

Why the ordering is symbols by name and integers numerically: the book
leaves "keys can be ordered in some way (e.g., numerically or
alphabetically)" to the implementation. `compareKeys` compares `VSym`
keys lexicographically by name and `VInt` keys numerically, and
refuses a mixed comparison -- an IllegalArgumentException, since
mixing key types in one table is a caller error, not a runtime event
the table reports. The KDoc and the scaffold say the reader must
define the ordering their table assumes; the tests pin both orderings,
including the numerical one where string order would disagree (2
before 10, and 17 walking to a null leaf between them).

Why an in-place tree and not a fresh copy per insert: the section is
about mutation through a fixed handle -- the header pair there, the
root node here -- and the exercise asks for the records to be
"organized", not rebuilt. Overwrite writes `node.value`; insert writes
one `left`/`right` slot of the parent. The book's later material
(3.3.3's footnote about the first backbone pair representing the
table) is the same idea one node deep.

What the tests say: `E3_26Test.kt` finds all five inserted symbols out
of insertion order, walks misses to null leaves on both sides of the
stored range, overwrites an existing key without disturbing its
neighbor, and checks integer keys against the numeric ordering.

Class: `T` (mechanical translation of a describe-and-implement row).

Deviation: none.
