# Exercise 5.30: errors signaled inside the evaluator

Both parts are built, and the places that needed the change are the two
the exercise's answer names.

(a) `lookup-variable-value` answers a distinguished condition code for
an unbound variable: a tagged word whose tag no object-language value
can carry, because the object language has no tagged words. `ev-variable`
tests the code and goes to `signal-error`.

(b) `apply-primitive-procedure` checks every application: a wrong
operand count, `car` of a non-pair, or division by zero returns the
condition code instead of escaping the machine, and `primitive-apply`
tests it. Both paths land in the base controller's `signal-error`, which
stops the machine with the object-level message.

The pinned session runs the caught failures in order (`car` of the
symbol `5`, division by zero, the unbound `no-such-variable`, a wrong
operand count), then the clean factorial that still answers `120`, so
the checks did not change the correct path's answers. The machine word
reserve is what keeps a condition code off every user value: the reader
cannot produce a value with the condition tag.
