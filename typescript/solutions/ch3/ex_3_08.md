# Exercise 3.8: operand evaluation order

## Approach

The exercise is about the host language's order for evaluating a
procedure call's operands, so the probe is deliberately the raw
JavaScript closure the book asks for: one captured `let` holding the
running product of all arguments seen so far. Each call multiplies its
argument into the state and answers the product, so whichever call
executes first decides what the second call sees. JavaScript's spec
(ECMA-262) fixes left-to-right evaluation, so where Scheme leaves the
question open, TypeScript answers it; the exercise verifies the
defined order rather than discovering it.

## Numbers

With a fresh probe, `f(0) + f(1)` answers `0`: `f(0)` runs first,
zeroes the state, and `f(1)` returns `0`. Calling in the reverse
order, `f(1) + f(0)`, answers `1`: the first call sees state `1` and
returns it. A fresh probe always answers `arg * 1` on its first call.

## Map class

A (the map's class for TypeScript: order defined; exercise verifies
it).

## Deviation

This is the one exercise whose local state is a raw `let` closure, on
purpose: an `Effect` version would test `Effect.gen`'s sequencing,
which is textual, not the language's operand order. The map's note
sanctions exactly this ("TS `let`"), and `Effect.gen`'s left-to-right
`yield*` sequencing is worth a sentence in the prose, not a probe.
