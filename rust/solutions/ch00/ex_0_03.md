# Exercise 0.3: predict-then-compile

## Method

Each of the five cases documented as doctests on `crates/ch00/src/sec_0_3.rs`
is a minimal, self-contained snippet chosen to isolate exactly one borrow-
checker rule. The doctests themselves are the ground truth: cases expected
to fail are annotated `compile_fail` (with the specific expected error code,
`E0382`, `E0502`, or `E0106`), and cases expected to succeed are plain
`rust` doctests that also assert their own postcondition. `cargo test --doc`
runs all five on every gate, so the verdicts below are not an assertion made
in prose; they are compiler output, checked continuously.

## Verdict by case

- **A (rejected, E0382).** `let b = a;` moves `a`'s `String` into `b`.
  `String` does not implement `Copy` (it owns a heap allocation), so the
  move is real: the old binding `a` no longer denotes a valid value, and
  reading it is a compile error, not a runtime hazard.
- **B (accepted).** `first` borrows `v[0]` and is used once, in the
  `println!`, before `v.push(4)`. Under non-lexical lifetimes, a borrow's
  live range ends at its last use, not at the end of its enclosing block;
  by the time `push` needs `&mut v`, `first`'s borrow has already ended, so
  there is no conflict.
- **C (rejected, E0502).** Swapping the order so `println!("{first}")`
  comes after `v.push(4)` forces `first`'s live range to span the `push`,
  which needs `v` mutably while `first` still holds it immutably. This is
  the same code as B with one line reordered, which is the point: the
  rule is about live ranges, not the mere presence of a later mutation.
- **D (rejected, E0106).** `fn shout() -> &str` promises to return a
  borrowed `&str`, but the only candidate, `s`, is a `String` this function
  owns and drops when it returns. There is no lifetime parameter that could
  make this legal, because there is no input borrow for the return value to
  be tied to; the compiler rejects it at the signature, before it even
  reaches the body.
- **E (accepted).** `a.clone()` allocates a new `String` with the same
  contents and hands it to `b`; `a` is untouched, so both bindings remain
  valid afterward.

## Why encode this as `[bool; 5]`

The exercise could be answered purely in prose, but chapter 0's own rule is
that every exercise with an observable, checkable answer gets a test, not
just a discussion. Each case's compile-or-reject outcome is exactly such an
answer, so `verdicts()` returns it as data, and the exercise's own
`predictions()` is checked against it directly.
