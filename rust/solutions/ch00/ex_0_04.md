# Exercise 0.4: an accumulator built from two closures

## Approach

`make_accumulator` builds one `Rc<Cell<i128>>` and moves a clone of the
`Rc` into each closure:

```rust
let total = Rc::new(Cell::new(0i128));

let add = {
    let total = Rc::clone(&total);
    move |amount: i128| {
        let new_total = total.get() + amount;
        total.set(new_total);
        new_total
    }
};

let reset = move || {
    let old_total = total.get();
    total.set(0);
    old_total
};
```

`Rc::clone` bumps a reference count and hands back a pointer to the *same*
`Cell`; it does not duplicate the `i128` inside it. Both closures now hold
a handle to one shared cell, so a `set` through either one is visible to
the other on its next `get`. `Cell::set`/`get` work through a shared
(non-`mut`) reference, which is exactly what two independently-owned
closures need: neither closure has (or could have) a `&mut` to the other's
capture.

The two closures have different concrete (compiler-generated) types, so the
function returns them boxed as trait objects,
`(Box<dyn Fn(i128) -> i128>, Box<dyn Fn() -> i128>)`, aliased as
`ch00::sec_0_7::Accumulator`.

## Why a plain `i128` does not work

Consider the naive version:

```rust
let mut total: i128 = 0;
let add = move |amount: i128| { total += amount; total };
let reset = move || { let old = total; total = 0; old };
```

`i128` is `Copy`. A `move` closure captures by value, and for a `Copy` type
"by value" means the closure gets its own independent bitwise copy of
`total`, not a handle to one shared `total`. This code does compile (each
closure closes over its own copy just fine), but it does not do what the
exercise asks: calling `add` mutates only `add`'s private copy, `reset`
mutates only its own separate copy, and the two closures never observe each
other's updates. The bug is silent, not a compile error, which is exactly
why the exercise asks for an explanation rather than just a prediction.
`Rc<Cell<i128>>` fixes this by making both closures hold a pointer to one
allocation instead of two independent values that merely started out equal.

## Test

`add(10)` then `add(15)` then `reset()` then `add(1)` yields `10, 25, 25, 1`
in the reference solution, confirming the running total truly is shared and
that `reset` both returns the prior total and zeroes it for the next call.
