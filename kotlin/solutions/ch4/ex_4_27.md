# Exercise 4.27: the lazy identity

## Approach

The delay rules give the sequence before any run. The book's
`w (id (id 10))` maps onto `outer(thunk { id(10) })` in this edition:
`outer` applies at once -- a compound procedure's body is entered, its
unannotated parameter arriving as a transparent thunk -- so `count`
climbs to 1, and returning the parameter hands back the delayed argument
itself, still unforced. Reading `w` through `force` runs the inner
computation (`count` climbs to 2, the value 10 is stored in the memo);
re-reading `w` answers from the memo and `count` never climbs again. The
forcing instrument counts the re-force as an attempt without a
computation (4 attempts, 3 computations).

## Map class

`T`; the objective (observe when a delayed argument computes, and that it
computes at most once) is unchanged. The explicit `thunk`/`force` pair
stands where the untyped evaluator let a thunk leak into `w`, because the
typed surface auto-forces transparent parameter thunks on reference.

## Deviation

The session's shape is re-cut to the typed surface: the delayed value is
an explicit thunk, so the first `count` boundary (1) is preserved exactly
rather than the old accidental leak.

## Answer

- `lazyIdentityTranscript() == "1\n10\n2\n10\n2\n"`: the outer
  application enters once, the inner computation runs at first demand,
  and the memo answers every later read.
- Instrument: `forceAttempts == 4`, `computations == 3` (the memoized
  re-force is an attempt without a computation).
