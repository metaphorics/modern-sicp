# Exercise 1.5: Ben Bitdiddle's applicative-order test

## Approach

`p` is a procedure whose only action is to call itself, forever:
`fn p() -> !` whose body is the recursive call `p()`.

```rust
pub fn p() -> ! { p() }

pub fn test(x: i64, y: i64) -> i64 {
    if x == 0 { 0 } else { y }
}
```

`p` returns `!` (it never returns a value, by construction) and `test`
returns an ordinary `i64`, matching the book's zero test:
`fn test(x: i64, y: i64) -> i64` that answers `0` when `x == 0` and `y`
otherwise.

## What `test(0, p())` demonstrates

Rust evaluates a function call's arguments before the call, the same as
every mainstream language: applicative order. `test(0, p())` therefore
evaluates `p()` first, which never returns, so the call to `test` itself
never happens and the program hangs (or, in practice, never gets past
building the argument). This is exactly Ben's diagnostic: an
applicative-order run hangs on `test(0, p())`, while a normal-order one
would pass `0` and the uncalled `p()` through unevaluated, find that
`x == 0` inside `test`'s body, and return `0` without ever forcing
`p()`.

## The normal-order stand-in

Rust cannot switch its whole evaluation strategy, but a single call site
can defer evaluation by taking a thunk instead of a value:

```rust
pub fn test_lazy(x: i64, y: impl FnOnce() -> i64) -> i64 {
    if x == 0 { 0 } else { y() }
}
```

`test_lazy(0, || 5)` builds the closure but never calls it, because `x ==
0` short-circuits before `y()` is reached; this is the one place in the
section where the book's normal-order alternative is directly
constructible in Rust, and the test proves it by using a `Cell<bool>` flag
that a called closure would flip and an uncalled one leaves untouched.

## Test

`test(0, 5) == 0`, `test(1, 5) == 5`, `test_lazy(0, || 5) == 0`, and a
side-effecting thunk passed to `test_lazy(0, ...)` never runs (`called`
stays `false`), confirming the laziness. The test also
type-checks that `p: fn() -> !` compiles, without calling it.
