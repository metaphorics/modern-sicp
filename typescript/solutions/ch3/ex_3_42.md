# Exercise 3.42: serialize once outside dispatch

## Approach

Ben's version is spelled literally: the serializer wraps the withdraw and
deposit builders once, at account creation, and the dispatch answers
those very procedures. The comparison is computed, not argued: the same
four-operation concurrent workload runs under real fibers on the text's
dispatch-time account and on Ben's pre-built account, and the allowed
outcome set of two concurrent withdrawals is enumerated on the step
scheduler for the serialized chunks, with the raw two-step withdraws as
the contrast.

## Pins

Computed: the concurrent workload (withdraw 20, withdraw 30, deposit 10,
deposit 5) ends at 65 on both account versions; the serialized-chunk
pair set is {60} for both because both wrap the operations with the very
same serializer instance, so the set of mutually excluded procedures is
unchanged. The unserialized contrast set is {60, 80}, the 80 being the
lost update both versions rule out. So the change is safe: creating the
serialized procedures at account-creation time instead of per message
changes allocation timing, not allowed concurrency. The one caveat the
code shows: the pre-built versions are bound to one balance cell at
construction, exactly like the book's closures, which `make-account`
already promised.
