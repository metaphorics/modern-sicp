## Exercise 2.73: data-directed deriv

Approach: `OperatorExpr` gives `Sum`, `Product`, and `Pow` each their own
variant, and `derivDataDirected` recognizes `Num` and `Var` directly
before routing every other case through a `DerivTable` keyed by the
operator string. That table is a private one for this exercise, not the
runtime's `OpTable` (2.4.3's own installed one): its handlers return
`OperatorExpr`, a different value type than the runtime `Op`'s `Value`,
so a separate `put`/`get` pair sharing the same discipline is the right
fit rather than a forced reuse.

Part (a): `Num` and `Var` cannot join the table-driven dispatch because a
number or a variable carries no operator to index the table by — the
operator symbol *is* the type tag for a compound expression, and an atom
has none. `derivDataDirected` still special-cases them first, exactly as
the book's rewritten `deriv` does.

Part (b): `installSumRule` and `installProductRule` implement
`d(a1+a2)/dx = da1/dx + da2/dx` and the product rule, installed under `"+"`
and `"*"`.

Part (c): `installPowRule` adds the power rule of exercise 2.56,
`d(u^n)/dx = n u^(n-1) du/dx`, under `"**"` — one more `put`, no change to
`derivDataDirected` or the other two rules.

Part (d): flipping the table to `get(operator, "deriv")` only renames the
axes the table is keyed by; nothing about `derivDataDirected`,
`installSumRule`, `installProductRule`, or `installPowRule` would change
in substance, only the argument order of every `put`/`get` call.

Class: A, per the map — the idea survives (the table technique, the same
three rules), but the statement changes because `OperatorExpr` is a
sealed hierarchy fixed at compile time rather than an open tag: adding a
new *expression shape* still means a new variant and a new arm in
`derivDataDirected`, unlike the book's fully open `cond`. Adding a new
*rule* for an existing shape, which is what parts (b) and (c) actually
ask for, stays purely additive through the table either way — that
distinction is the map's "hard spot" for this section, verified directly
by the second test: the sum rule's answer does not change before or
after `installPowRule` runs.

Deviation: none in substance.
