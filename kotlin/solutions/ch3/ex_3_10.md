## Exercise 3.10: the let version binds in the same frame

Approach: `makeWithdrawLet` in `E3_10.kt` replaces the parameter
`balance` with a local `var balance` assigned from the parameter
`initialAmount`. In Scheme, `(let ((balance initial-amount)) (lambda
(amount) ...))` desugars to `((lambda (balance) (lambda (amount) ...))
initial-amount)`: an extra procedure call, and therefore an extra frame,
sitting between `make-withdraw`'s own frame and the lambda's captured
environment. Kotlin's local `var balance = initialAmount` is not a call;
it is an ordinary statement that adds a binding to the frame
`makeWithdrawLet`'s own call already built. So where the book's figure
for this exercise would show two frames (one for `make-withdraw`,
binding `initial-amount`, and one for the inner `let`-lambda, binding
`balance`), the Kotlin structure has exactly one: `makeWithdrawLet`'s
call frame, holding `initialAmount` and then `balance` side by side, and
the returned lambda captures that single frame.

Trace: for `w1 = makeWithdrawLet(100L)`, `makeWithdrawLet`'s call opens
one frame, E1, binding `initialAmount: 100` and then `balance: 100`; the
returned lambda's captured environment is E1. Calling `w1(50L)` opens a
second frame binding `amount: 50` whose enclosing environment is E1, so
the lambda body finds `balance` there, decrements it, and returns 50.
`w2 = makeWithdrawLet(100L)` opens a second, independent E1-shaped
frame, so `w1` and `w2` never see each other's `balance`.

Same behavior: `E3_10Test.kt` drives the sequence `50, 60, 20, 40`
through both `makeWithdraw(100L)` (the parameter version from 3.2.3) and
`makeWithdrawLet(100L)` and asserts the two produce identical results at
every step, matching the book's claim that the two versions behave the
same.

How the structures differ: the book's two versions differ by one frame
(the `let`'s own frame, absent from the parameter version). In Kotlin
they do not differ at all: both `makeWithdraw` and `makeWithdrawLet`
build exactly one call frame and capture exactly one cell in it, because
neither a function parameter nor a local `var` is itself a nested call.
The `let`-adds-a-frame teaching point is specific to Scheme's
`let`-as-syntactic-sugar; Kotlin has no equivalent extra indirection to
observe.

Class: `R` (the exercise is a Scheme frame-counting question; this
edition replaces it with the Kotlin question of whether the frame count
differs, and it does not).

Deviation: none.
