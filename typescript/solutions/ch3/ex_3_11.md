# Exercise 3.11: where the account state lives

## Approach

The book asks for the environment structure of the make-account
sequence, where `acc`'s local state is kept, and how `acc2`'s state
stays distinct. The edition traces the whole sequence:
`makeAccountTraced` logs the frame each factory call opens, the balance
cell it creates inside it, and the dispatch it returns;
`runTraced` logs the request frame each call opens and the cell change
it makes; `renderAccountStructure` renders the end-of-sequence
structure from the log. The account is the edition's tagged-dispatch
`makeAccount` shape: the arms read and write one `Ref` captured by the
dispatch.

## Pins

The sequence (acc with 50, deposit 40, withdraw 60; acc2 with 100)
answers 90 and 30. The cell changes in the log are exactly
`acc: 50 -> 90` and `acc: 90 -> 30`; two `CellCreated` events name the
two cells (`acc` initial 50, `acc2` initial 100), and
`Object.is(acc.balanceCell, acc2.balanceCell)` is false. acc2 is
untouched (its cell still reads 100) and answers `40` to a withdraw of
60 from its own 100 afterward, while acc's cell still reads 30. The two
dispatches are distinct objects (`Object.is` false) over distinct
cells; the shared parts are the one `make-account` procedure object
both calls applied and the arm code its body specifies. The rendered
structure pins all of this in one drawing computed from the log.

## Map class

`R: diagram per-factory closure state`. The drawing became a log of
factory frames, cells, and dispatches, with the sharing question
answered by identity checks on the cells and the dispatches.

## Deviation

The book's `make-account` defines `withdraw`, `deposit`, and `dispatch`
as internal definitions; the edition's account (3.1.1) spells the arms
inline in the dispatch, so the traced factory logs "arms and dispatch
born in the factory frame" rather than three separate internal binds.
The internal-definitions behavior the book leads with is the `sqrt`
listing of 3.2.4 in the section module. The traced factory returns the
cell beside the dispatch so the identity questions have a handle; the
untraced `makeAccount` of the section module keeps the book's surface.
