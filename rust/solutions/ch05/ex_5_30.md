# Exercise 5.30: error signaling inside the evaluator (T)

## Approach

Both parts are built, and the places that needed the change are the
two the exercise's answer names.

(a) `lookup-variable-value` answers a distinguished condition code
for an unbound variable: a tagged word carrying the reserved
`unbound-variable` name and the detail message, which no user value
can spell. `ev-variable` tests the code and goes to `signal-error`.

(b) `apply-primitive-procedure` checks every application: a wrong
operand count, `car` of a non-pair, or division by zero returns the
condition code instead of escaping the machine, and
`primitive-apply` tests it. Both paths land in the base controller's
`signal-error`, whose `user-print` reports the condition's detail and
whose return to the driver loop leaves a stack the next interaction's
`initialize-stack` cleans, exactly the book's arrangement.

## Map class

`T`.

## Sample answer

The checking evaluator runs the caught failures and pins each
printed detail: `car` of a symbol answers `car: not a pair: 5`,
division by zero answers `division by zero`, the unbound variable
answers `unbound variable: no-such-variable`, and a wrong operand
count answers `cons: needs two arguments`. A clean factorial still
answers `120`, so the checks did not slow the correct path down or
change its answers.
