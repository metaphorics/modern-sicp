# Exercise 3.41: should balance reads serialize

## Approach

Ben's variant is spelled literally: one per-account serializer wraps
withdraw, deposit, and now the balance message too. The demonstration
runs one balance read forked against one in-flight 25 withdrawal on both
accounts, under real Effect fibers; the fiber scheduler interleaves at
the accounts' three-step windows in FIFO order, so each report is a
measured run, not an argument.

## Pins

Text account (unserialized read), computed: the withdrawal accesses 100
and suspends in its window, the reader reads 100 there, the withdrawal
commits 75. Report {readValue: 100, finalBalance: 75}. Ben's account,
computed: the reader parks on the serializer until the withdrawal
releases, then reads the settled 75. Report {readValue: 75,
finalBalance: 75}. So Ben's scenario exists exactly as a stale snapshot:
the unserialized reader can observe 100 after the withdrawal has begun.
What no run produces is damage: money is conserved, the final balance is
75 either way, and the withdraw/deposit stream is serialized regardless.
Ben is wrong that serialization of reads is needed for correctness; the
read only ever observes a value some complete state actually had. What
the extra serialization buys is freshness for readers, at the price of
queuing every read behind every in-flight update.
