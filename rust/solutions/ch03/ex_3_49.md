# Exercise 3.49: ordering avoidance fails scenario

## Approach

The scenario is a transfer chain: each account names, in its own
serializer-protected records, the next account of the chain, so a
process cannot know which account it needs next until it already
holds the current one -- the resource set is unknown exactly when the
first lock is taken, and "always enter the lower number first" has
nothing to work on. The solution walks one link: hold the first
account's serializer, read its next pointer, and take that account's
serializer while still holding the first. Two processes start at
accounts whose chains point into each other (0's next is 1, 1's next
is 0); each ends up holding its first account and waiting for the
account the other holds. The halt-aware run ends the spin and records
both processes deadlocked: no numbering discipline could have ordered
acquisitions whose targets were discovered under the locks themselves.

## Map class

`T`. The demand for a defeating scenario is the statement's own; the
chain form (a resource you must hold to learn the next resource) is
this solution's concrete instance of the hint's
"acquire some shared resources before knowing which additional shared
resources it will require".

## Deviation

None. The deadlock is the genuine blocked-forever kind, ended only by
the demonstration's halt handle, which the section module provides
for exactly this purpose.
