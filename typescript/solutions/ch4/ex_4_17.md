# Exercise 4.17: the extra frame of scanned-out definitions

## Approach

The answer is carried by running the same body under three evaluators built
in one shared dispatch: the module's sequential `evaluate`, a scanned
evaluator whose lambda clause installs a scanned `make-procedure`, and a
same-frame variant whose application pre-binds the scanned names. The scan
wraps the set!s in the let's own derivation, a lambda application, so the
extra frame is structural: one application per call whose only bindings are
the `*unassigned*` pre-bindings. The design answer extends the call frame
once, with parameters plus the scanned names pre-bound to `*unassigned*`,
then runs the set!-only body, so no second frame is built. Frame counts are
observed with the public `env.vars`/`env.parent` chain: a program returns a
closure, and the closure's environment depth is the frame count.

## Numbers

`(define (f) (define a 1) (define b (+ a 1)) (+ a b))` then `(f)` answers
`3` under all three evaluators. `(define (g) (define a 1) (lambda () a))`
then `(g)` returns a closure whose environment depth is `2` under the
sequential evaluator, `3` under the scanned evaluator, and `2` under the
same-frame variant: the two make-procedure variants differ by exactly one
frame. Applying the same-frame closure answers `1`.

## Class and deviations

Translated row. Deviations: the scan emits the let's derivation (a lambda
application) rather than a `let` expression, because this edition's
evaluator has no let clause; only leading defines are scanned, as in the
book's example; and the dispatch is written out in full because the
module's eval helpers recurse through the module's `evaluate` and would
leave lambdas nested inside define, set!, and if forms unscanned.
