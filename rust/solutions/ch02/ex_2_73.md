# Exercise 2.73: data-directed differentiation

## Approach

The exercise's `Expr` keeps the section 2.3.2 shape (`Num`, `Var`,
`Sum`, `Product`) and adds `Pow` for part (c) and `Atan`, dormant until
2.73a installs its rule. `operator` maps each application variant to
its symbol and answers `None` for `Num` and `Var`; the type itself
states part (a)'s answer: a number or a variable carries no operator to
index the table by, so `deriv` keeps them as `match` arms and only
dispatches through the table once an operator exists. Part (b) installs
the sum and product rules under `("deriv", "+")` and `("deriv", "*")`;
part (c) installs exercise 2.56's exponentiation rule under
`("deriv", "**")`, valid for a literal integer exponent. On the book's
probes, `(+ x 3)` differentiates to `1`, `(* x y)` to `y`, and
`(** x 3)` to `(* 3 (** x 2))`. Part (d) swaps the two key arguments to
`put` and `get` (`deriv_flipped` looks up `(operator, "deriv")` instead
of `("deriv", operator)`), and every rule and constructor is unchanged;
only the two calls that build and read the keys move.

## Map class

`A`: an enum for the expression variants replaces the book's type tags,
and the operator symbol derived from each variant plays the role of the
type tag the table dispatches on, matching the map's Rust class for
this row.

## Deviation

The table itself is this exercise's own: a `(op, tag) -> handler` map
with the same shape as the section's `OpTable` (real table, ordered
keys, `put` overwrites, `get` returns the absent option) but holding a
handler typed over this exercise's `Expr` rather than the section's
dynamic `Value`, since expressions here are a closed enum, not tagged
runtime data.
