## Exercise 3.26: organize records as a binary tree

Approach: `TreeTable` stores mutable `TreeNode` records under one root.
Lookup follows one root-to-leaf path; insertion follows the same path,
overwrites a matching node, or attaches a new node at the first empty
child slot.

Why the keys have a defined order: `compareKeys` orders `Symbol` keys by
name and `Whole` keys by numeric value. It rejects comparisons between
those key types.

What the tests say: they cover both orderings, misses on either side of
stored keys, overwrite without changing a neighbor, and the point where
string order would disagree with numeric order. Mixed key types raise
`IllegalArgumentException`.

Class: T (the operation's cost follows tree depth).

Deviation: record keys use the native `Datum` variants `Symbol` and `Whole`.
