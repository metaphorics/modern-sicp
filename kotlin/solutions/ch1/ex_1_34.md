## Exercise 1.34: f(f) does not type-check

Approach: `f(g) = g(2)` demands `g: (Long) -> Long`. `f(::square)` and
`f { z -> z * (z + 1) }` both satisfy that and return 4 and 6. `f`
itself has type `((Long) -> Long) -> Long`, which is not a
`(Long) -> Long`, so `f(::f)` fails to compile with an argument-type
mismatch; the source file records the exact refused line and the
compiler's message as a comment, since a line that fails to compile
cannot live in a buildable file. SICP's own `(f f)` is untyped, so it
runs one step further before failing: `(f f)` reduces to `(f 2)`,
which tries to apply the non-procedure 2 and signals "The object 2 is
not applicable" at run time. Kotlin's static types catch the same
error at compile time, before the program ever runs.

Class: A (adapt); the map's reason is "type checker rejects it" for
all four editions, and this rationale is exactly that discussion. The
tailored idea 1.34a (compare compile rejection with runtime failure) is
the paragraph above; it was not chosen as this section's one addition.
