# Exercise 5.34: compiling iterative factorial

The recursive factorial must resume its pending multiplication after each recursive call, so each call keeps a return continuation and grows the stack with the input. In the iterative definition, the call to `iter` is the last expression in the procedure body. The compiler emits a direct compiled-procedure-entry transfer for that call instead of assigning a new return continuation. The existing continuation is reused, so the loop does not accumulate one stack frame per iteration.

`iterativeFactorialCompilation` exposes the relevant distinction in the generated listing: it counts compiled-branch tail transfers and saves, then runs monitored factorial calls at three input sizes and reports their maximum depths. The source does not claim that every operation in the whole program is stack-free; the invariant is that the recursive `iter` calls do not grow the stack with the number of iterations.

The Kotlin measurement is derived from `CompilerConfig`, the actual rendered statement list, and `runCompiledMonitored`; the depth values are not copied from the book's machine.
