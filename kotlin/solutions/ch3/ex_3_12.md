## Exercise 3.12: append copies, append! splices

Approach: `E3_12.kt` keeps the two procedures side by side so the
contrast is the code. `append` recurses exactly as in 2.2.1, consing a
fresh pair for every element of `x` onto `y`; the base case returns `y`
itself. `appendBang` computes `lastPair(x)` and calls `setCdr` on that
one pair, then returns `x`. `lastPair` walks until the current pair's
`cdr` is `VNil`, which is why it must take a `VPair` and not a `Value`:
the type system now refuses the `appendBang` call on an empty `x` that
the book had to state as an error in prose.

Why `append`'s result shares nothing with `x`: every pair of `z` came
from a `cons` call, so `z` is a fresh spine over copies of the elements.
`x` still ends in `VNil`, which is what the first missing `<response>`
shows: `(cdr x)` prints `(b)` after `append`, unchanged. The second
`<response>` is `(b c d)`: `appendBang` found `x`'s last pair (the `b`
cell) and pointed its `cdr` at `y`, so the very same cell that used to
end `x` now continues into `(c d)`. `w === x` is true: the function
returned its argument, mutated.

What the tests say: `E3_12Test.kt` runs the book's session in order and
asserts the printed values, including the two answers the exercise
leaves blank. A plausible bug fails immediately: an `append` that reuses
`x`'s pairs, an `appendBang` that builds a new list instead of splicing
(`w === x` becomes false), or a `lastPair` that stops one pair early
(the spliced `x.cdr` would print `(b)` and `lastPair(w) ===
lastPair(y)` would fail).

Class: T (direct port; only the host-language names changed).

Deviation: none.
