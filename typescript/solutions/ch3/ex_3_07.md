# Exercise 3.7: `makeJoint` shares one account

## Approach

A joint account is not a second balance but a second password over the
first account's `Ref`: the wrapper translates the new password to the
original one and forwards the request, so peter and paul spend the same
money. Membership is checked once, at make-joint time, with a
balance-neutral probe (a zero deposit through the original password);
the book's "in order for the make-joint operation to proceed" becomes
that probe failing with the underlying account's `IncorrectPassword`.
A wrong password at the joint name fails `IncorrectPassword` without
reaching the balance.

## Numbers

`makeJoint(peterAcc, "open-sesame", "rosebud")` lets `rosebud`
withdraw 40 from peter's 100 (60 left); peter's next withdraw of 60
answers 0, the shared balance observed; after a 30 deposit the joint
name withdraws 25 to 5. `open-sesame` at the joint name fails
`IncorrectPassword` (and so does `rosebud` at the original). A wrong
original password makes `makeJoint` itself fail `IncorrectPassword`,
with the balance untouched.

## Map class

T (plain port; ocaml holds the tailored 3.7a addition, the read-only
capability).

## Deviation

The book does not specify how `make-joint` verifies the original
password; the zero-deposit probe answers it without observable state
change, and it builds on the 3.3 account (not 3.4), so lockout counts
are not perturbed by joint creation.
