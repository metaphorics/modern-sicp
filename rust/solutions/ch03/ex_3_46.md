# Exercise 3.46: test-and-set race window

## Approach

The book's plain-procedure `test-and-set!` reads the cell and then,
if it read false, writes it -- two separate operations with a window
between them. Two demonstrations pin the window. The forced one
schedules read, read, write, write between two processes over the
cell, and both provably acquire a mutex that admits one: the timing
diagram made executable. The stress one releases two real threads
against the same cell a thousand times with a widened window, and
counts the runs where both got in. The module's plain-procedure
version works on a `Cell<bool>`, which is neither `Send` nor `Sync`,
so Rust refuses to offer it to a second thread at all; the solution
spells the same two separate operations over an `AtomicBool` (plain
load, then plain store) so the window exists on real parallel
hardware. The identical stress over the module's atomic
`TestAndSetCell` never once admits two processes: the indivisible
compare-and-swap is the fix the text says multiprocessing hardware
provides.

## Map class

`T`. The non-atomic implementation and the timing-diagram demand are
the statement's own.

## Deviation

The shared cell moves from `Cell<bool>` to `AtomicBool` because the
race demonstration needs two threads and `Cell` cannot cross one;
the two-operation structure the exercise is about is preserved
exactly, one load and one store.
