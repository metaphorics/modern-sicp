## Exercise 2.90: sparse and dense behind one interface

Approach: [TermListRepresentation]`<L>` is the seam the book's exercise
asks for (`empty`/`isEmpty`/`first`/`rest`/`adjoin`), implemented once
by [SparseTermsRep] (a `PersistentList<Term>`, `adjoin` conses) and once
by [DenseTermsRep] (a `PersistentList<Num>`, `adjoin` prepends a
coefficient, padding any gap above the current top with zeros).
[addTermsVia]/[mulTermByAllTermsVia]/[mulTermsVia] are `add-terms`/
`mul-term-by-all-terms`/`mul-terms` written once against the interface,
so both providers share one algorithm. `ex_2_90` runs the book's sum and
product through both providers and checks they agree, in sparse form,
via [toSparseTerms].

Class: A, per the map; one generic interface with two implementations
is the natural Kotlin shape for "two kinds of term-list packages,"
mirroring how the book asks the system to "distinguish different
representations in the same way we did in the complex-number example."

Deviation: two bugs surfaced while proving this exercise, both now
fixed. First, `DenseTermsRep.adjoin` originally required the adjoined
term's order to equal the list's current size exactly; but
`mul-term-by-all-terms` adjoins the highest-order product term *first*,
against an empty accumulator, so the order can sit far above the size:
`adjoin` now pads the gap with zero coefficients instead of rejecting
it. Second, `toSparseTerms`'s projection needed to drop zero
coefficients when comparing dense to sparse results, the same
representational difference exercise 2.89 hit. Neither fix changes what
either provider computes, only how the two results are compared or how
far apart an adjoined term's order may sit from the list it joins.
