# Exercise 5.30: errors signaled inside the evaluator

Part (a), the unbound variable, and the book's wrong operand count
cannot reach the machine in the subset: admission resolves every name
and type-checks every application before evaluation, so both programs
are rejected as type-invalid. `ex_5_30 ()` shows the two rejections.

Part (b) is built for the runtime failures a checked program can still
reach, the failures the grammar lists: division or remainder by zero
and an out-of-range array access. `apply-primitive-procedure` and
`apply-binary` answer a condition code for such a failure instead of
stopping the machine: a constructor value tagged `#condition`, a name
no guest constructor can spell, carrying the failure's description.
The controller tests `condition?` after both operations and branches to
`signal-error`, which reports the failure and stops its program with a
sentinel error, so a later item of the same program never runs on the
condition value; `run` then goes on to the next interaction. A
failure of the machine itself, such as an unknown label, still stops
it with its own error. A `List.map` callback runs on the base
evaluator through the public `make_evaluator` and `eval`, so its
division by zero fails the `List.map` application, which becomes the
condition on the signaling machine; the callback never sees the
condition codes.

`ex_5_30 ()` runs the caught failures on one evaluator, each pinned: an
`Array.get` out of bounds, a division by zero, a remainder by zero, a
division by zero inside a `List.map` callback, and a failure with a
second item after it, which never runs, then a clean factorial
that still answers `120` on the same evaluator. It also reports the
saved words the failed call leaves on the stack: the machine stopped
mid-call, while the base evaluator, given the same division, stops
with its error.
