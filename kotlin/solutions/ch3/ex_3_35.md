## Exercise 3.35: the squarer as a primitive constraint

Approach: `squarer` in `E3_35.kt` follows Ben's outline with the holes
filled. The object expression is the book's `me`; `newValue` is
`process-new-value`: read `b`; if `b` is valueless, take the value of `a`
(or do nothing if that is missing too) and store its square in `b`; if `b`
is negative, raise the book's `error` call; otherwise store
`round(sqrt(b))` in `a`. `forgetValue` is `process-forget-value`: retract
both connectors, then run `newValue` again so whatever the other side still
holds is re-derived. The factory connects the constraint to `a` and `b` and
returns it, so the caller holds the same handle the connectors do.

Why (an `error` here, an `Either` nowhere): the connector layer reports its
one domain conflict, a contradiction, as `Either.Left`, but the interface
this exercise extends has no result to fill: `Constraint.newValue()` is a
notification, not a request. The book handles the impossible input the same
way, by calling `error` from inside the propagation; here that is Kotlin's
`error("square less than 0: SQUARER $v")`, and the exception surfaces from
the very `setValue` call that woke the constraint, which the test observes
with its message intact. Roots go through `round(sqrt(...))`, exact for the
perfect squares the tests use; a non-square `b` would round to the nearest
root, which is the honest statement of what a `Long` connector can hold.

What the tests say: `E3_35Test.kt` drives both inference directions the
multiplier version of 3.34 lacked (b = 25 gives a = 5, and a = 7 gives
b = 49), then forgets `a` and watches both sides fall and re-derive from
b = 36 to a = 6, and finally checks the negative-square error, message
included. Any branch-order mistake (reading `a` before `b`, forgetting the
`newValue` tail of `forgetValue`) fails one of these directly.

Class: `T`.

Deviation: none.
