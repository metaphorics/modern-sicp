# Exercise 2.77: nested apply-generic

## Approach

The Figure 2.24 object is built by
`make_complex_from_real_imag(&table, 3.0, 4.0)`, so `z` is
`(complex (rectangular (3 . 4)))`: two tag layers carried in one
runtime `Value`. Before the fix the table holds `magnitude` only
under `(rectangular)` and `(polar)`, so the outer lookup misses and
dispatch ends in `SchemeError::UserRaised` with the message
"No method for these types", the error Louis reports.

The fix is `install_complex_selectors`: the four selectors of the
statement, `real-part`, `imag-part`, `magnitude`, and `angle`, are put
under `(complex)` keys. Each entry is the generic selector of the same
name rather than the 2.4.2 dispatch closure of the statement's
snippet: it looks its operation up in the table again, against the
inner rectangular or polar tag. `counting_apply_generic` is the
section's `apply_generic` with a `Cell<u32>` counter threaded through
the installed entries, so the trace question gets a number instead of
a hand count.

On the probe, `magnitude` answers `5` and the count is `2`, the
asserted pair. The two invocations are the two tag layers: the outer
call dispatches on `(complex)` into the installed entry, and that
entry dispatches again on `(rectangular)` into the rectangular
package's handler, which computes the hypotenuse. That is why the fix
works: the outer tag now finds a handler, and the handler re-enters
dispatch one layer down, where the method has been there all along.

## Map class

`A`: nested tagged values need layered enums. The runtime has a single
`Value` enum, so a nested tagged datum is tagged again inside its own
contents; handling it takes one dispatch layer per tag, and the
counted pair of invocations is exactly those two layers.

## Deviation

None.
