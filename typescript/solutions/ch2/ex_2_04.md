# Exercise 2.4: the procedural pair as the function pair type

## Approach

The representation is the statement's `(m) => m(x, y)` with its type
made explicit: `Pair<A, B> = <R>(m: (x: A, y: B) => R) => R`. A pair is a
function that hands both parts to a selector; `carPair` applies it to the
selector `(p) => p`, `cdrPair` to `(_p, q) => q`. The substitution
verification the hint asks for is one line: `carPair(consPair(x, y))` =
`consPair(x, y)((p) => p)` = `((p) => p)(x, y)` = `x`.

The generic result parameter `R` is what lets `carPair` and `cdrPair`
request different result types (`A` and `B`) from one and the same pair
value, the point the main text's `ProcPair<T>` had to give up; no cast and
no `any` is needed anywhere.

## Numbers

The law is asserted on numbers (`1`, `2`), on distinct object identities
(`toBe`, not structural equality), and on a mixed-type pair
(`consPair("k", 7)`).

## Map class

`A` (map: "closure pairs need function pair type"): the idea survives
unchanged, and the statement names the type the closure pair needs - the
generic selector-continuation function type - which the host checks before
anything runs.

## Deviation

The statement's names `cons`/`car`/`cdr` become `consPair`/`carPair`/
`cdrPair` in the solution so the file stays self-contained beside the
section module's tuple glue; the types and bodies are the statement's.
