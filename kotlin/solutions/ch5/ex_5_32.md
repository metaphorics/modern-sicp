# Exercise 5.32: the symbol-operator fast path

A combination whose operator is a symbol does not need to evaluate an arbitrary operator expression. The explicit-control evaluator can take the operator name directly to `lookup-variable-value`, set `proc`, and continue with operand evaluation. `evApplicationFast` branches on `symbol-operator?` before the general path saves `env` and `unev`; a non-symbol operator still follows the ordinary `eval-dispatch` path. This is the evaluator-side version of the compiler's register-preservation optimization, applied to a syntactic case the evaluator can recognize.

Alyssa's proposal misses the cost and limits of runtime special cases. The evaluator would have to test expression shape on every evaluation, while the compiler can use expression structure and register-use analysis to omit saves when they are unnecessary. Adding dispatch branches can reproduce some optimizations, but it does not remove the runtime checks or make every compiler analysis free.

In Kotlin, `evApplicationFast` replaces only the named evaluator-controller fragment, and `symbolOperatorOp` supplies the operation consumed by the controller. The solution test checks that the symbol call returns `36`, the lambda operator call returns `42`, and the monitored baseline transcript contains its maximum-depth output with `144`. These checks cover both branches; the `144` observation is from the baseline monitored evaluator run, not a claim about the fast evaluator's push count.
