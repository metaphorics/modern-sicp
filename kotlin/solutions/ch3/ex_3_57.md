# Exercise 3.57: counting the additions behind fibs

## Approach

The memoized side builds the counting fibs as a pair stream through a
local tie cell: each element carries the Fibonacci value and the number
of additions performed so far, and every zip head bumps the running
count once. Because each memoized tail runs its zip at most once,
element n costs one addition for every element past the first two, so
the count at index n is n - 1 (0 for n <= 1); the test pins the whole
table for n = 2 to 15 and the law term by term.

The unmemoized side pays the re-derivation tree: a plain lambda delay
re-runs its zip on every force, and the zip's two argument streams
re-derive the whole tree below them before their heads are added. The
meter walks the same construction cold, paying one fresh derivation of
every element: one derivation of element i costs d(i) = d(i-2) +
d(i-1) + 1 with d(0) = d(1) = 0 (one per zip head, both predecessors
re-derived), and computing element n pays d(2) through d(n). The pinned
table for n = 2 to 15 is 1, 3, 7, 14, 26, 46, 79, 133, 221, 364, 596,
972, 1581, 2567, derived mechanically and cross-checked by a python3
mirror of the recurrence; 2567 at n = 15 against 14 memoized is the
exponential claim the statement asks for (count > 1000 vs 14).

## Map class

`T` (map row 3.57: Kotlin T).

## Deviation

The contract's law names the naive tree-recursive count fib(n+1) - 1
(0-indexed fib): that is the cost d(n) of one fresh derivation of
element n -- 986 at n = 15 -- which falls short of the > 1000 claim the
same contract pins. The construction's own arithmetic resolves it: the
walk that computes element n re-derives every element below it, so the
counted total is the sum of d(2) through d(n), which closes as
fib(n+3) - n - 2 = 2567 at n = 15 and exceeds 1000 from n = 13 on. The
per-derivation count keeps the tree-recursive shape the statement
names; the walk total is what the exponential claim measures, and both
tables are pinned from the same meter.
