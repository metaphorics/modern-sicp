# Exercise 4.31: lazy and lazy-memo parameter declarations (translate)

The map class is `T`. The statement's extended `define` syntax meets
the subset's closed grammar, which has no parameter annotations and
accepts no new syntax. The declaration therefore rides on the
parameter's name, which the pinned checker admits unchanged: `b_lazy`
is the text's `(b lazy)`, delayed without memoization; `d_lazy_memo` is
`(d lazy-memo)`, delayed through a memoized thunk cell; every other name
is strict. The evaluator is the applicative-order direct evaluator of
`Sec_4_1.open_eval` with two clauses replaced: application of a closure
binds each parameter per its declaration (a strict operand evaluated at
the call, a lazy one wrapped as a thunk of the operand in the caller's
environment), and a variable bound to a thunk is forced where it is
read, recording the result only for a `_lazy_memo` name. Ordinary
definitions keep their strictness, so the extension is upward
compatible, and the demonstration shows it: the same `pick` with a
strict parameter dies on the armed operand.

The demonstration: a `_lazy` parameter never read saves an armed
`string_of_int (1 / 0)` (`pick` prints `taken`); the four-way
declaration `f a b_lazy c d_lazy_memo` evaluates the strict parameters
at the call, forces the `_lazy` one once per read and the `_lazy_memo`
one once in total, and the counting identity reads 5; `twice` under
`_lazy` runs `id` twice where `twice_m` under `_lazy_memo` runs it
once, so `count` reads 2 and then 3.
