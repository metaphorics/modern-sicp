# Exercise 3.69: triples and Pythagorean stream

## Approach

The complete first-coordinate cut, built on the section's own `pairs`
and `interleave`: the head triple is `(s0, t0, u0)`, and the rest
interleaves the triples whose first coordinate is `s0` -- `s0` consed in
front of every pair `(j, k)` of `pairs` over the two tails -- with the
recursion `triples` over the three tails. The two sides are disjoint
and cover every `(i, j, k)` with `i <= j <= k`, and `interleave` keeps
both infinite sides alive. Running that construction over the integers
and testing `i*i + j*j == k*k` answers the Pythagorean triples in the
stream's own order. The scan is bounded and iterative: the section's
`stream_filter` recurses eagerly across each run of non-matching
triples, and the gaps between Pythagorean hits in the interleaved order
run thousands deep, so the eager filter overflows the stack; the
iterative stream cursor walks a measured prefix instead and stops at
the sixth hit. The walked spine of `300_000` memoized nodes would also
overflow the stack on its recursive drop, so the scan suppresses that
drop with `ManuallyDrop`, on the reclamation-at-process-exit terms the
stream implementation's own design document sets for the streams it
cannot drop.

## Map class

`T`. The statement translates whole: `triples` produces the triples
`(S_i, T_j, U_k)` with `i <= j <= k` over three infinite streams, and
the Pythagorean filter answers the triples with `i <= j` and
`i*i + j*j = k*k`. The one Rust wrinkle is laziness hygiene: the port's
eager-recursion profile (both `stream_filter`'s scan and the recursive
drop of a long memoized spine) is linear in the gap and spine lengths,
so the answer takes the bounded cursor scan instead of the literal
`stream_filter` composition.

## Deviation

The task sketch suggested a scan prefix of 2000-20000 inside a second;
measurement falsified that: the interleaved order reaches the
first-coordinate branches at an exponential index, and the six
Pythagorean triples land at stream indices 19, 607, 6127, 14079, 81791,
and 292863. The bound is therefore `300_000` and the debug run costs
about 1.2 seconds -- kept because the six pinned triples are exactly
the canonical ones, `(3,4,5) (6,8,10) (5,12,13) (9,12,15) (8,15,17)
(12,16,20)`, in the stream's own order.
