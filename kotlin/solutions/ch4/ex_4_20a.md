# Exercise 4.20a: nested letrec shadowing (edition addition)

## Approach

The program is the statement's shape exactly: the outer `letrec` binds `f`
recursively; inside a recursive call, an inner `letrec` binds `f` again (
the shadow, initialized to `(lambda (m) 0)`) and lists `k` before `f`, so
`k`'s initializer `(f (- n 1))` references the shadowed name before the
inner binding is assigned.

Under the edition's scoping rule the variables a `letrec` binds are in
scope, but unassigned, while its initializers run. The inner `f` therefore
shadows the outer recursive `f` from the first inner initializer onward,
and `k`'s reference reads the reserved inner binding: the 4.20 evaluator
raises the typed premature-read fault naming `f`. Read with the outer
binding in scope instead (a discipline where a binding arrives only after
its initializer, the way a plain `let` behaves), that same reference names
the outer recursive `f`, and the program recurses. The contrast pins this
by swapping exactly the inner form for a plain `let` and running both
programs on the same 4.20 evaluator: nothing but the scoping rule differs.

## Map class

`T` for the 4.20 machinery it builds on. `4.20a` is the edition addition
chosen for Kotlin and has no upstream map row.

## Deviation

The outer-in-scope reading is demonstrated with the inner form as a plain
`let` on the same evaluator rather than a second `letrec` scoping: the
same program modulo the inner form, which isolates the scoping rule the
exercise asks about. A nested-let lowering of the inner `letrec` was tried
first and discarded: it also hides the outer `f` from the outer recursion
itself (`Error: unbound variable: f`), which confounds the contrast.

## Answer

From the actual runs (`E4_20aTest` pins both transcripts exactly):

- Shadow program, edition's scoping rule:
  => `Error: type mismatch: f is read before it is assigned`.
- Same program with the inner form a plain `let` (outer binding in scope):
  => `1`; `(f 2)` recurses through the outer `f` down to 0 and the
  answer climbs back up as `k`.
