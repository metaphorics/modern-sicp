# Exercise 3.57: fib additions with memoized delay

## Approach

The counting is put where the additions happen: a `counting_add_streams`
with the exact delay shape of the module's `add-streams`, incrementing
an `Rc<Cell<u32>>` once per stream element it builds. The counting
`fibs` is 0 consed onto 1 consed onto the sum of its own tail and
itself, with the meter riding every clone. Producing element `n` then
forces one new cell per index from 2 up to `n` -- the seeds 0 and 1
need no addition -- and each cell is built exactly once because every
tail thunk is memoized: exactly `n - 1` additions, measured as 9 for
element 10 and 19 for element 20, and a second identical walk meters 0
because it re-reads the shared memoized spine. The contrast is the
tree-recursive `fib` of 1.2.2 behind a call meter: `fib(15) = 610`
costs 1973 calls (`2 x fib(16) - 1`). A plain-lambda `delay` re-runs
its expression on every force, so each tail re-addition would spawn the
whole prefix again -- the call tree is exactly what the stream flattens
into n - 1 memoized additions, linear in n instead of exponential.

## Map class

`T`. The statement translates whole. The Rust wrinkle is that the
edition's `delay` is already the book's `memo-proc` (`Lazy` memoizes),
so the exponential branch cannot be run against the real stream; the
statement's demonstration is carried by the call-metered tree
recursion, which is the same computation the unmemoized tails would
perform.

## Deviation

None. The counts 9, 19, 0, and 1973 are measured by running, not
derived on paper.
