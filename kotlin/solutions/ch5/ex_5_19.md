# Exercise 5.19: breakpoints

The breakpoint machine is the last one-loop override. A breakpoint
names a label and an n; `BreakpointMachine.execute()` checks the
breakpoint table before every instruction and parks the machine
(set `waitingAt`, return from the loop) just before the instruction
under that label is executed for the n-th time, and again before each
later n-th: the counter counts the arrivals whose instructions
executed, and the machine parks when the counter's remainder mod n
reaches n - 1.

The semantics the book leaves open, and this edition pins, is what
`proceed` does with the pending stop. Proceeding consumes it: the
resumed arrival runs and counts once (the counter has one owner, the
execution loop), so the machine next stops at a later n-th arrival,
not at the same one forever.

`breakpointSession()` runs the whole story on the gcd machine and
`E5_19Test` pins the four lines:

- With a breakpoint on `test-b` at n = 2, `start()` parks before the
  second arrival, one full division step done: `break at test-b:
  a = 40, b = 6`. The mid-run register read is the proof the machine
  is inspectable while parked, which is the point of a breakpoint.
- `proceed()` consumes that stop and the machine parks once more
  before the fourth arrival, two division steps further on: `break at
  test-b: a = 4, b = 2`. A proceed that double-counted the consumed
  stop would park again at the very next arrival (b = 4), and this
  line is the regression pin against that.
- The session's loop proceeds through the last stop and the run
  completes: `finished: gcd(206, 40) = 2`.
- `cancelBreakpoint` removes the breakpoint and a fresh `start()` goes
  straight through: `cancel and restart: gcd(206, 40) = 2`.

`cancelAllBreakpoints` is the book's cancel-all over the same table,
and setting a breakpoint on a label the controller never defines is a
host `IllegalArgumentException` naming the label, a caller bug rather
than machine behavior.
