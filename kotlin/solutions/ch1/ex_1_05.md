## Exercise 1.5: applicative order, re-cut as eager versus lambda

Approach: Kotlin always evaluates the arguments of a call, so the direct
translation `test(0, p())` diverges exactly as Ben's applicative-order
interpreter does, and no normal-order interpreter is on offer. The re-cut
makes the contrast expressible: the eager `Long` parameter evaluates its
operand although the taken branch ignores it (the probe counts 1), while a
`() -> Long` parameter defers the operand into a lambda body that the
taken branch never invokes (the probe counts 0), and
`testDeferred(0) { p() }` returns `0` with the diverging call sitting
unevaluated in the slot. The eager shape matches the book's
applicative-order interpreter; the lambda shape is the explicit, per-
argument spelling of normal order, and Kotlin has no automatic global
equivalent.

Class: T (translate), with the re-cut of the companion's divergence list
item 2 supplying the lambda-parameter half of the demonstration. Deviation:
the probe counts evaluations instead of running `p()` to divergence, which
no test can assert.
