## Exercise 3.20: tracing shared state through the procedural pair

Approach: SICP's exercise asks for environment diagrams of the Scheme
dispatch pair; this edition replaces the drawing with a trace of the
same object in Kotlin terms, and `E3_20Test.kt` asserts each step of the
trace through code. The implementation is the section's `PairProc` over
`proceduralCons`: one call frame binding two `var` slots, `carCell` and
`cdrCell`, captured by the returned object's four methods.

The trace of the replaced session: `val x = proceduralCons(VInt(1),
VInt(2))` opens frame E1 with `carCell = 1`, `cdrCell = 2`, and returns
an object whose methods all refer to E1's slots. `val alias = x` binds a
second name to the *same* object: no new frame, no new slots, just a
second entry pointing at E1. `alias.setCar(VInt(17))` calls `setCar` on
that object; its body finds `carCell` in E1 and overwrites it. `x.car()`
then reads the same slot through the same captured frame and answers
17. The state never lived in `x` or `alias`; it lives in E1, and both
names reach it only through the object.

What the contrast says: a fresh `proceduralCons(VInt(1), VInt(2))` opens
a fresh frame E2 with its own two slots, so the same `car()` request
there answers 1. Two calls to the constructor produce two objects whose
method bodies are shared compiled code over two unrelated frames:
exactly the account/sharing conclusion of exercise 3.11, and the reason
the book's dispatch version and this interface are the same idea.

What the tests say: the first test pins the replaced session's answer;
the second pins the fresh-frame contrast, asserting the new object's
slots still read 1 and 2 and that it is not the same object as `x`. An
implementation whose `setCar` writes a copy of the slot, or whose
selectors read constructor parameters instead of the captured `var`s,
fails the first test; a `proceduralCons` that returns a shared singleton
fails the second.

Class: R (SICP's exercise is about Scheme environment diagrams; this
edition replaces it, keeping the number and teaching the same shared-
captured-state material in Kotlin terms).

Deviation: none.
