## Exercise 3.22: the queue as a message-passing object

Approach: `makeQueue` in `E3_22.kt` opens one call per queue, binding
two local `var`s, `front` and `rear`, both starting null; the returned
`object : MessagePassingQueue` expression's four members capture those
two cells. The bodies are the same pointer surgery as the section's
`Queue` -- hang the fresh cell off the rear pointer on insert, advance
the front pointer on delete -- but the state lives in the closure, not
in class fields: the object is an anonymous class with no fields at
all.

Why the interface: exercise 3.11's account already established the
edition's message-passing shape -- a small interface for the messages,
a factory function, an object expression whose overrides are the
captured closures. The book's `dispatch` on message symbols becomes
the object's own method dispatch; there is no `when` over `m` because
Kotlin resolves the message at the call site. The interface is named
`MessagePassingQueue`, not `Queue`, because the section's class owns
that name in the same package and the exercise's point is the
difference between the two shapes.

Why the two implementations look alike but are not the same: the
class version keeps its pointers in `private var` fields declared
once for all instances; each `makeQueue()` call here allocates fresh
local cells, so the sharing story of 3.11 repeats -- every queue has
its own `front`/`rear` pair, all queues share the compiled member
bodies. `E3_22Test.kt` observes both facts: two queues print
independently after one receives an insert, and `q1 === q2` is false.

What the tests say: the book's session runs through the closure queue
(insert a, insert b, delete, delete) and `printQueue` reports `(b)`
then `()`; a delete on a fresh queue is `Either.Left(EmptyQueue)`; a
queue emptied to nothing accepts a new insert, which the `rear = null`
reset on delete is what makes possible.

Class: `T` (mechanical translation).

Deviation: none.
