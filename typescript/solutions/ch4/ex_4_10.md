# Exercise 4.10: one evaluator, two syntaxes

## Approach

The special forms move into a syntax table: a map from marker name to a
handler that receives the marker call's arguments and builds a node of
the shared syntax. The evaluator knows nothing about markers — both
surfaces produce the same `Expr` data — so `evaluate` and
`applyProcedure` are untouched, and every nested reading, sequence, and
application goes through the same table, so procedure bodies follow the
surface of the reader that runs them. Two tables are installed: the
standard marker names (`fn`, `branch`, `seq`, `set`, `pick`), and the
same handlers under names spelled backwards (`nf`, `hcnarb`, `qes`,
`tes`, `kcip`).

## Numbers

The square program answers `49` under both tables: `const square =
fn("x", x * x); square(7)` in the standard surface and `const square =
nf("x", x * x); square(7)` in the reversed one. `branch(3 > 2, 1, 0)`
answers `1`, and `hcnarb(3 > 2, 1, 0)` also answers `1`. Cross-table, a
marker is just a name: `branch(...)` read with the reversed table stays
an application and fails with `unbound-name` on `branch`, and
`hcnarb(...)` with the standard table fails with `unbound-name` on
`hcnarb`. Bodies follow their reader: `fn("x", branch(x > 0, 1, -1))`
answers `1` at `5` and `-1` at `-5`, and `seq(set("seen", 1), 7)` is
`7` after writing `seen`.

## Class and deviations

Translated row. Deviations: the statement says to illustrate the idea,
so the table covers the five forms this solution installs, and the
second surface is the book's own joke spelling, names written
backwards. The cross-table fault category migrates from the old
`UnboundVariable` to the engine's `unbound-name`, keeping the lesson
that a tag is only a name.
