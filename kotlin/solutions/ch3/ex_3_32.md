## Exercise 3.32: why a segment's actions must run first in, first out

Approach: the pinned order, straight from the code: two actions added
to one agenda segment at time 5 run as `["first", "second"]`, because
`ActionQueue.insert` appends at the rear and `delete` removes from the
front -- the 3.3.2 queue's two-pointer discipline, so the oldest
scheduled action in a segment is always the next one run.

Why the order must be FIFO: an action's output depends on the wire
state it observes when it runs, and actions scheduled into the same
segment are responses to changes that all land at the same simulated
instant. They must run in the order their causes happened, oldest
first, so each action sees the accumulated state of all the changes
scheduled before it. The exercise's and-gate trace makes the failure
mode concrete: inputs a1, a2 at 0, 1 change to 1, 0 in the same time
segment. The a1 change schedules `out = and(1, a2) = 0` at t + 3; the
a2 change schedules `out = and(a1, 0) = 0` at t + 3, after it in the
same segment. Run FIFO, the gate re-evaluates twice and settles at 0,
which is correct -- a1 and a2 never have the same value at this
instant. Run LIFO (a plain list, added and removed at the front), the
a2 response would run first and the a1 response second -- the order of
causes reversed -- and in circuits where the intermediate evaluation
differs, the gate schedules its intermediate output later than its
final one, so the wrong value is the one that lands. The agenda is the
simulator's notion of causality; LIFO would run effects before their
causes within an instant.

What the tests say: `E3_32Test.kt` pins the two-action same-segment
order, then pins the full deletion order across two segments (time 3's
pair before time 5's, each pair FIFO): `propagate` drains segments in
time order and hands each segment's actions back oldest-first, ending
with the agenda empty. That is the whole discipline -- time orders the
segments, the queue orders the actions inside one.

Deviation: none.
