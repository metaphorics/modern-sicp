# Exercise 4.17: the extra frame of the scanned-out let

## Approach

The statement asks for the environment structures at `<e3>`; this edition
makes the difference observable by counting frames live. A `frame-depth`
primitive walks the environment chain a compound procedure captured, root
included, and the probe closes a lambda over the frame the body's
definitions ran in: `(define (f x) (define b (+ x 1)) (lambda () b))`, then
`(define g (f 20))`. Under the plain sequential rule the defines land in
the parameter frame, so `g`'s chain is parameter frame + global = 2; under
the 4.16 scan-out the body lowers to a `let` whose application pushes one
more frame, so `g`'s chain is let frame + parameter frame + global = 3. A
top-level lambda anchors the counter at 1 in both runs.

Behavior cannot differ: the extra frame only relocates the bindings. Every
name the body defines sits one frame out, but each `set!` rebinds the
reserved cell in place, the assignments still run in source order, and any
lookup that resolved through the parameter frame before now passes through
the transparent `let` frame first and finds the same values, which the pin shows by answering 21 both ways.
pin shows by answering 21 both ways. The frame is avoidable the way the
book's note suggests: reserve the defined names directly in the parameter
frame at application time, and the simultaneous scope costs one frame, the
same as the sequential rule.
