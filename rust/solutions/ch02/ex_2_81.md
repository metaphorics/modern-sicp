# Exercise 2.81: self-coercion

## Approach

Louis's two identity coercions go in next to the section's conversions
through the same `put_coercion` interface, and `exp` is installed only
under `(scheme-number scheme-number)` using `checked_pow`. Part (a) is
then a two-complex call: `louis_apply_generic` misses
`(exp (complex complex))`, finds the `complex` to `complex` identity,
coerces, and recurses on the argument list it started with, so the
same miss recurses forever. The solution caps the recursion at a depth
of 64 and turns the loop into `SchemeError::UserRaised` with
"recursion did not terminate: Louis's self-coercion loop", the
infinite recursion the exercise predicts, made observable.

Part (b) is answered by `fixed_apply_generic`, which looks the
operation up first and gives up at once when the two tags agree. The
same two-complex `exp` call now fails at once with the plain
"No method for these types" error, so Louis was wrong:
`apply_generic` needed the same-type guard, not the identity entries.
Both failures are asserted through `expect_err` and the two message
fragments.

Part (c) falls out of the guard: with coercion skipped for same-type
arguments, the identity entries are never consulted, so installing
them is harmless. The operation still works where it belongs, and
`exp` of `2` and `3` answers the asserted `8`.

## Map class

`A`: coercion table needs heterogeneous entry types. Louis's identity
rows go in through the same `put_coercion` interface that carries the
section's cross-type conversions, so same-type and cross-type entries
are one mechanism, and the pathology the exercise probes is a property
of that table's same-type rows.

## Deviation

The depth cap is the one addition: the book's system recurses until
resources run out, while the solution stops at 64 and reports the
loop, so the test can assert part (a)'s answer instead of hanging.
