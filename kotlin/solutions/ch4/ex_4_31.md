# Exercise 4.31: `lazy` and `lazy-memo` parameter declarations

## Approach

The declaration syntax rides the typed parser: [parseAnnotatedExpr]
recognizes the procedure-definition shape whose parameter list carries
`(name lazy)` or `(name lazy-memo)` entries and lowers it to an ordinary
lambda plus a modes datum under the reserved constructor
`*annotated-lambda*` -- a name no program text can reach, the
`*unassigned*` trick of 4.16. Evaluating that application builds the plain
procedure and records the per-parameter modes keyed by procedure identity.

[AnnotatedParams] extends the strict base evaluator, because the point is
upward compatibility: unannotated programs keep the base discipline
exactly. Annotated applications bind per mode -- strict parameters
evaluate at the call, `lazy` parameters become call-by-name thunks,
`lazy-memo` parameters become call-by-need thunks -- and forcing happens
at the demand sites the section named: an `if` predicate, the values a
strict primitive will use, and the driver's answer. `apply` re-binds an
applied annotated procedure per its modes from already-evaluated values.

The counting session declares `(f a (b lazy) c (d lazy-memo))` with body
`(list a b b c d d)` and call arguments `(id 1)`, `(id (+ 2 3))`,
`(id 4)`, `(id (* 5 6))`: the strict pair counts 2 at the call, each `b`
use recomputes, `d` computes once -- `(1 5 5 4 30 30)`, count 5. The
all-`lazy-memo` declaration computes each delayed parameter at most once:
count 4. The upward-compatibility pins: a `lazy` parameter skips its
dangerous argument entirely (`(g (/ 1 0))` answers 7), the strict
counterfactual dies eagerly.

## Map class

`T` unchanged; the mixed-count pin (5) is the same shape as the Rust
sibling's, with this edition's own body.

## Answer

From the actual runs (`E4_31Test` pins all four transcripts):

- Mixed declaration => `(1 5 5 4 30 30)`, count 5.
- All `lazy-memo` => `(1 5 5 4 30 30)`, count 4.
- `lazy` parameter => `7`; strict parameter => `Error: division by zero`.
