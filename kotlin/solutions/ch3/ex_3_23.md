## Exercise 3.23: a deque over doubly linked cells

Approach: the deque is a chain of `DPair` cells, each carrying its
item, the cell behind it (`prev`), and the cell ahead of it (`next`),
plus the class's two end pointers `front` and `rear`. Insert splices
one cell onto the named end and repoints that end; delete reads the
item out of the end cell and moves the end pointer one cell inward,
also clearing the surviving neighbor's opposite slot so no pointer
into a detached cell survives. Both ends cost a constant number of
writes; nothing ever scans.

Why a local `DPair` class instead of the section's `VPair`: the book
says "represent deques using pairs", and the natural first move is a
chain of `VPair`s plus a parent map to recover the backward pointer.
That keeps the one-way pairs of the section and bolts on a side table:
two structures to keep in step on every mutation, and the map's
entries are themselves mutable state to clean up on delete. A cell
that already has a `prev` slot is the same object count as the book's
doubly linked pairs with one slot added, keeps every operation a
pointer write, and fails loud rather than silently desyncing a side
map; the trade is that these cells are not `Value`s and cannot live in
other `VPair` structure, which the deque never needs. The footnoted
warning about printing a cyclic structure stays true here in a second
way: `prev`/`next` chains cycle pairwise, so a `DPair` must never be
handed to `println`.

Naming: the book's `front-insert-deque!` and friends become
`frontInsert`, `rearDelete`, and so on, methods on the deque, per
the section's convention, with the `!` dropped because the `set`
prefix rule does not apply and the method names read as ordinary
mutators. Empty ends answer `frontDeque`/`rearDeque` with null where
the book signaled, matching the section's selector; the four delete
paths report `Either.Left(DequeError.EmptyDeque)` like the queue's
`delete`.

What the tests say: `E3_23Test.kt` interleaves front and rear traffic
four deep and reads both ends back out in order; empty deques fail at
both ends with `EmptyDeque`; a deque emptied from either end accepts
new traffic, which the mutual `front = null`/`rear = null` resets on
delete are what make possible.

Class: `T` (mechanical translation; the cyclic-printing footnote is
kept as prose, and the representation choice is this one).

Deviation: none.
