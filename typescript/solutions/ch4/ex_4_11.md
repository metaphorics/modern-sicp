# Exercise 4.11: frames as association lists

## Approach

A frame becomes one list of name-cell bindings instead of two parallel
maps: `AListEnv` holds an ordered `Binding` list plus its parent, held
so that define and set can write it while every environment node
sharing the frame sees the change. `lookupInAList` scans the entries of
the current frame for a matching name and walks the parent chain when
absent; `setInAList` finds the first frame that binds the name and
rewrites that entry's cell in place; `defineInAList` conses a fresh
binding onto the current frame, shadowing outer ones; `frameVariables`
reports a frame's own names. Lookup, set, and define are tested
directly over a two-frame chain.

## Numbers

With `a = 1` in the outer frame and `b = 2` in the inner: looking up `b`
from the inner frame answers `2`, looking up `a` walks out and answers
`1`, and `zz` fails with `unbound-name`. After writing `10` to `a` from
the inner frame, the outer frame's own lookup answers `10`: the write
landed in the shared entry. Defining `c = 3` in the inner frame leaves
`frameVariables` of the inner frame as `["c", "b"]` and of the outer
frame as `["a"]`, and `c` is unbound from the outer frame's point of
view. Setting an unbound `zz` fails with `unbound-name`.

## Class and deviations

Translated row. Deviations: a binding is the engine's name-cell binding
record rather than the book's two-element list, since the frame must
share mutable cells with the evaluator's own semantics (including the
`mutable` flag that rejects const rewrites); and the edition's own
frames are maps, which stay untouched — this file builds the book's
association-list representation beside them and re-derives the same
visible semantics.
