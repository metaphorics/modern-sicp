# Exercise 4.31: lazy and lazy-memo parameter declarations

## Approach

The declaration `(name lazy)` or `(name lazy-memo)` is object-language
syntax on the parameter list: a bare name is strict, the
upward-compatible default. The guest grammar has no parameter-mode
syntax, so the modes ride on the argument discipline the declaration
denotes: a strict parameter arrives as its value, a lazy parameter as a
recomputing thunk called per demand, and a lazy-memo parameter as one
delayed cell forced per demand under the memoized experiment. The
unforced lazy parameter is exactly what lets `pick` return its second
arm while the first arm would fault on demand.

## Numbers

`pick` answers `taken`, the lazy parameter unforced. The `f` run
answers `[1, 5, 5, 4, 30, 30]` with count `5`: two strict calls, two
recomputed lazy demands, one computed lazy-memo demand. `g`'s lazy
parameter demanded twice runs twice (count `7`), `h`'s lazy-memo
parameter demanded twice runs once more (count `8`). The counts match
the sibling editions' sessions.

## Class and deviations

Translated row. Deviation: the declared modes are carried by the
argument discipline rather than a mode table keyed by procedure
identity — the guest parameter grammar is closed — so a lazy parameter
is a zero-argument recomputing thunk and a lazy-memo parameter is one
shared delayed cell. Malformed mode specifications cannot exist in
this spelling.
