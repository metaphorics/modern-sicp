# Exercise 5.25: normal-order evaluation in the controller

The plan, made before the controller was written:

1. Thunks are the shared thunk cells of the lazy experiment
   (`Value.thunk`): a delayed expression and its environment, or the
   memoized value after the first forcing. One operation,
   `delay-operand`, builds them, and they travel in `V` words.
2. The environment is unchanged: a parameter is bound to its thunk
   cell, and reading the variable forces it.
3. The controller changes in exactly three places, each a spliced
   replacement of a kept fragment: the argument loop delays each
   operand and adjoins the thunk (no saves, no dispatch, which is the
   laziness); `ev-variable` forces a delayed binding through
   `eval-dispatch` and memoizes the value in the cell; `primitive-apply`
   forces every delayed argument, one at a time through the same
   forcing entry, before the primitive sees the list.

The code follows the plan: `lazy_argument_loop`, `lazy_ev_variable`,
and `lazy_primitive_apply` are the three replaced fragments. Because
the thunk is a cell, memoization is per thunk, as in the book; the
earlier edition's per-binding deviation is gone.

`ex_5_25 ()` pins the three proofs: `factorial 5` still answers `120`;
`always_42 (1 / 0)` answers `42`, while the strict base evaluator stops
with a division by zero; and `use_twice (bump 1)` answers `1 1` with
the counter left at `1`, so the thunk of `bump 1` ran once. The
same session with `memoize-thunk` a no-op answers `1 2` with the
counter at `2`: without memoization the thunk runs once per
reference, and the strict base controller would agree with the `1 1`
line, so the `1 2` line is the one that singles out memoization.
