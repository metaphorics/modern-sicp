# Exercise 4.20: letrec as a derived expression

## Approach

The parser leaves every unrecognized form an application, so `(letrec
((name init) ...) body ...)` arrives in `step` as an `AppE` whose operator
is the `letrec` symbol. The override destructures the binding pairs and
body out of the application shapes (malformed forms raise the typed
`Parse` fault) and lowers the form exactly like 4.16's scan-out: one `let`
reserving every name with `*unassigned*`, one `set!` per name in source
order, then the body: the text strategy. It keeps the unassigned window
open only until each name's own `set!` runs, so source-order initializers
see earlier names assigned while genuinely premature reads still fail the
typed check. The same reservation check backs `lookupVariable`.

Part (b) is where Louis's reasoning is loose, and the lowering shows it: a
plain `let` evaluates its initializers before any frame holds the names,
so the lambda captured there can never see the `let`'s own binding (a
recursive `fact` under plain `let` fails unbound) while `letrec`
reserves the names first and makes the recursion legal.

## Map class

`T` (map row 4.20: Kotlin T).

## Deviation

None. The text-strategy lowering is the 4.16 scan-out applied to the
derived bindings; the alternative strategy of 4.18 was considered and
rejected, since its all-initializers-first window would reject the
statement's source-order initializers.

## Answer

From the actual runs (`E4_20Test` pins each transcript exactly):

- The even?/odd? `letrec`, `(f 10)` => `#t`.
- The factorial `letrec`, `(fact 10)` => `3628800`.
- The premature read, `(letrec ((x (+ y 1)) (y 2)) x)`:
  => `Error: type mismatch: y is read before it is assigned`.
- Part (b), the same recursion under a plain `let`:
  => `Error: unbound variable: fact`.
