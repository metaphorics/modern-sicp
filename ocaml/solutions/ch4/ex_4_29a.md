# Exercise 4.29a: the memoization toggle and forcing counters (this edition's addition)

The map class is `T`. This edition adds 4.29a because 4.29's question,
what memoization is worth, is answered there by object-language side
effects, while the evaluator's own bookkeeping stays invisible. The
addition reads that bookkeeping directly: one run of `square (id 10)`
per mode, the answer taken from the program's last binding and the
counts read from the run's `Sec_4_2.state` through `Sec_4_2.counts`,
not parsed from the transcript.

The counts partition cleanly. Forcing demand is a property of the
program text, so `forces` differs only by the one extra re-force the
unmemoized operand costs; `recomputations` doubles without memoization,
because memoization is what makes a second forcing cheap, turning it
into a memo hit; and without memoization a re-forced operand re-runs
`id 10`, which delays its operand again, so `allocations` grows too.
For `square (id 10)`: memoized `allocations=2 forces=3
recomputations=2 memo_hits=1`, unmemoized `allocations=3 forces=4
recomputations=4 memo_hits=0`.

Sample: `ex_4_29a ()` answers
`["100"; "allocations=2 forces=3 recomputations=2 memo_hits=1"; "100"; "allocations=3 forces=4 recomputations=4 memo_hits=0"]`:
the answer is 100 under both modes, and the counts assert what the
modes did to produce it.
