# Exercise 0.1: factorial by checked multiplication

## Approach

`factorial` is a direct recursive translation of the mathematical
definition: `0! = 1`, and `n! = n * (n-1)!` otherwise. The multiplication
uses `checked_mul` instead of `*`, and the whole function returns
`Option<i128>` by chaining through `?` on the `Option` returned by the
recursive call: if the recursive call already overflowed (`None`), the `?`
short-circuits and the whole call returns `None` without attempting a
multiplication on a value that doesn't exist.

```rust
fn factorial(n: u32) -> Option<i128> {
    if n == 0 {
        Some(1)
    } else {
        factorial(n - 1)?.checked_mul(i128::from(n))
    }
}
```

`largest_factorial_n` walks `n` upward from zero, calling `factorial(n + 1)`
each time, and stops as soon as that call returns `None`. It is a linear
search, not a closed-form calculation, because the exercise is about
observing where the checked arithmetic policy of section 0.1 kicks in, not
about deriving the bound analytically.

## Why 33

`33!` is `8,683,317,618,811,886,495,518,194,401,280,000,000`, which fits
under `i128::MAX`
(`170,141,183,460,469,231,731,687,303,715,884,105,727`). `34!` is
`295,232,799,039,604,140,847,618,609,643,520,000,000,000`, which does not.
The reference solution's test pins both values directly:
`factorial(5) == Some(120)`, and `factorial(34) == None`, `largest_factorial_n() == 33`.

## Why checked, not saturating or wrapping

`saturating_mul` would silently clamp to `i128::MAX` on overflow, which
looks like a valid answer and is not; `wrapping_mul` would produce an
arbitrary, unrelated number. Both hide the exact same bug this section's
overflow policy exists to surface. `checked_mul`'s `None` is the only one
of the three that tells the caller the true answer does not fit, which is
what `largest_factorial_n` needs to detect the boundary at all.
