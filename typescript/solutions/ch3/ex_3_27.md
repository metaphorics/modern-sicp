# Exercise 3.27: memo-fib

## Approach

The book's memoizer wraps the fib lambda in a local table: each call
first looks its argument up, answers a stored value when it is there,
and otherwise computes, stores, and answers. The edition keeps the
structure and replaces the diagram with a trace: `memoFib` computes
the n-th Fibonacci number over one local `Map` table, and
`memoFibTrace` answers the log of `Compute` (the wrapped lambda ran,
the result went into the table) and `Recall` (the table answered)
events, one per call. The book's point is built in: the
wrapped lambda's body must recurse into the memoized procedure
itself, so every nested call shares the one table and each value is
computed once, which is why the steps grow proportional to n.

## Pins

`memoFib(0)` is 0, `memoFib(1)` is 1, `memoFib(10)` is 55, and
`memoFib(30)` is 832040. Measured by running, the trace for n = 4 is
exactly Compute 4, Compute 3, Compute 2, Compute 1, Compute 0, Recall
1, Recall 2: the evaluator descends the n-1 spine to the base cases
before the recalls unwind, so the compute order is 4, 3, 2, 1, 0 and
not the 4, 3, 1, 2, 0 order a right-spine-first reading might suggest.
The five Compute events are fib 0 through 4, each computed once.
Running a fresh call builds a fresh table and walks the identical
trace.

## Map class

`A: Map memo; diagram becomes trace`. The book's environment drawing
of the shared table becomes the event log, and the once-per-value
structure the drawing shows is the Compute list.

## Deviation

The exercise statement's diagram question is answered by the trace,
per the map's note. Defining `memo-fib` as plain `(memoize fib)` would
break the sharing: the wrapped body would call the unmemoized `fib`,
no nested call would consult the table, and the log would show only
one Compute with no recalls, exponential time again.
