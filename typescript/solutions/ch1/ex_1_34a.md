# Exercise 1.34a: compile rejection versus runtime failure

## Approach

One program, two refusals. Typed, `f(f)` is rejected statically: exercise
1.34 records the tsc diagnostic. Erased - `fAny = (g: any): any => g(2)` -
the checker stands down and the program runs until the number 2 is applied.
The solution catches the thrown error and reports `{kind, message}` as a
value, this chapter's never-a-throw shape for domain failures.

## Numbers

The erased call throws `TypeError` with message `g is not a function`. The
mechanics: `fAny(fAny)` evaluates the body once with `g = fAny`, giving
`fAny(2)`; the second application finds `g = 2` in the parameter slot named
`g` and fails there - which is why V8's message names `g`. On proper
arguments the erased `fAny` still computes: `fAny(z => z + 7)` is `9`.

## Class and deviations

Tailored addition of this edition (map cell: "compare compile rejection with
runtime failure", `chosen: typescript`). One disclosure against the unit
brief: the brief anticipated pinning "the runtime RangeError", but the actual
host failure of the erased self-application is a `TypeError` - a stack
overflow is the only way this program could produce a `RangeError`, and it
recurses none. The pinned kind and message are the ones the host really
raises, verified by running the erased program.
