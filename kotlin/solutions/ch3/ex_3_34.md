## Exercise 3.34: why Louis's one-multiplier squarer cannot infer roots

Approach: `louisSquarer` in `E3_34.kt` is Louis's device verbatim:
`multiplier(a, a, b)`. The flaw is in the multiplier's inference order, and
the exercise is about seeing it in the code rather than fixing it. The
multiplier's `newValue` checks, in order: both factors known (multiply), or
product with exactly one factor known (divide). With `a` valueless, giving
`b` a value matches no branch that can produce `a`: the divide branches need
a factor to divide by, and both factor terminals are the same valueless `a`.
So a forced value on `b` sits there while `a` stays unknown: the device
cannot take square roots, which is the whole point of a squarer run
backward.

Why (observation instead of repair): the exercise says "explain", and the
edition's rule for trace-flavored exercises is to demonstrate through the
running device. `E3_34Test.kt` sets `b` to 25 on a fresh network and asserts
`a.hasValue()` stays false, then shows the forward direction still works
(a = 3 gives b = 9), and finally shows the device holding its stale
conclusion: after a = 3, forcing b = 25 comes back as
`Contradiction(9, 25)` because the multiplier still believes 9. That last
test is the flaw made observable twice over: the box propagates forward and
contradicts, but never reasons backward to a root.

What the tests say: the three tests together distinguish Louis's device from
a correct squarer. A "fixed" multiplier (say, adding a branch that divides
the product by a remembered factor) would make the first test fail, since
`a` would suddenly become 5, which is exactly the repair exercise 3.35
makes you build by hand as a primitive.

Class: `T` (the device and its failure reproduce in Kotlin unchanged; the
explanation is about constraint inference, not Scheme).

Deviation: none.
