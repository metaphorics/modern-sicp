# Exercise 0.2: change-counting, recursive and iterative

## The recursive process (section 1.2.2's algorithm)

`count_change_recursive` is the book's own recursive process, stated as a
rule: the number of ways to change `amount` using the first `kinds_of_coins`
denominations is the number of ways that don't use the largest of those
coins at all, plus the number of ways that use it at least once (which
reduces to change for `amount - coin_value` using the same denominations,
since a coin can be reused).

```rust
fn cc(amount: i64, kinds_of_coins: usize) -> i64 {
    if amount == 0 {
        1
    } else if amount < 0 || kinds_of_coins == 0 {
        0
    } else {
        cc(amount, kinds_of_coins - 1) + cc(amount - COINS[kinds_of_coins - 1], kinds_of_coins)
    }
}
```

This is a tree-recursive process: each call that doesn't hit a base case
makes two further calls, so the number of nodes in the recursion tree grows
much faster than `amount` itself.

## The iterative process

`count_change_iterative` computes the same count with a one-dimensional
table `ways`, where `ways[a]` accumulates the number of combinations of
coins seen *so far* that sum to `a`. Processing one coin denomination at a
time and updating `ways` left to right (`ways[a] += ways[a - coin]`) is the
standard "unbounded knapsack" combination count: because each denomination
is fully processed before moving to the next, a combination is never
counted more than once regardless of the order its coins could be added in.
This is the same recursion above, unrolled into a table instead of a call
stack.

## Depth comparison

`recursive_depth` instruments the same recursive algorithm to track the
deepest point the call stack reaches, by threading a `&mut u32` accumulator
through every call and updating it to the running maximum. For `amount =
400` with 5 denominations, the deepest path is the one that always chooses
"don't use this coin" until it runs out of denominations, then decrements
by the smallest coin (1) the rest of the way: that path is about
`amount + kinds_of_coins` calls deep, so `recursive_depth(400)` comes out
just over 400. `count_change_iterative`, by contrast, never recurses at
all: it is two nested `for` loops in one stack frame, so its "depth" does
not grow with `amount` the way the recursive version's does.

## Verified values

`count_change(100) == 292` is the classic result for this exact recursive
process with US coins, confirmed independently in Python before writing the
Rust; `count_change(400) == 26517` was computed the same way. Both
functions are asserted against both values, and against each other, in the
test.
