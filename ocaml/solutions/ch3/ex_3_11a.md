# Exercise 3.11a: object identity versus structural equality (addition)

The map's tailored-addition idea for this row is "object identity
versus structural equality", the hard spot the companion already
flagged for closure-captured state. The addition pins the section's
model to the two comparison operators OCaml actually provides, right
where the distinction pays off: two accounts built by separate calls
behave identically yet are different objects, and one account under
two names is one object that answers twice.

The checklist runs on three names: `acc` from `make_account 100`,
`twin` from a second `make_account 100`, and `alias` bound to the very
same object as `acc`. `acc == twin` is false (physical equality
compares the object, not the behavior), `acc == alias` is true (an
alias adds a name, not an object), and `acc = twin` raises
`Invalid_argument`; structural comparison cannot traverse functional
values, so for records of closures `==` is the only comparison the
language provides. The behavioral test the exercise contrasts with
identity stays decided by `=` on plain data: withdrawing 20 through
each account yields `Balance 80` twice, while the accounts remain
physically distinct.
