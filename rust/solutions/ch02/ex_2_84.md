# Exercise 2.84: successive raising

## Approach

The 2.83 raise entries are installed on the same table as the
arithmetic packages. The height test the statement asks for is
compatible with the rest of the system because it is the raise table
itself: `raise_step` looks up the `raise` entry for the value's tag
and answers `None` where no entry exists, so a type is higher exactly
when the other argument still has a raise path toward it. No global
ranking table is consulted, and a new package joins the ordering by
installing its own raise entry.

`apply_generic_raise` dispatches as usual first. On a miss with two
arguments it lifts whichever argument still has a raise entry,
alternating until the tags agree or both are stuck, with a bound of 8
steps. If the tags never agree, or the pair never moved at all, the
miss is `SchemeError::UserRaised`, "No method for these types";
otherwise the call retries on the raised pair.

The probes answer the statement's mixed arithmetic: `3 + (1 + 2i)`
raises the integer through rational and real into complex and answers
`(complex (rectangular (4 . 2)))`, and `1/2 + (0.5 + 1i)` raises the
rational twice and answers `(complex (rectangular (1 . 1)))`. The
plain `add` still misses on integer plus complex, asserted with
`plain.is_err()`, so the coercion lives in this dispatcher rather
than in the packages.

## Map class

`A`: successive raising needs tower ordering map. The ordering map is
the raise slice of the operation table, and successive raising is the
bounded loop that walks whichever argument's column still has an
entry.

## Deviation

None.
