## Exercise 3.37: constraint combinators in expression style

Approach: the five combinators in `E3_37.kt` each build one primitive box
onto one fresh connector and return that connector. `cPlus` is the book's
given `c+`; `cMinus` wires `adder(z, y, x)` so z + y = x, which makes z the
difference; `cMul` is a multiplier with `z` as product; `cDiv` wires
`multiplier(y, z, x)` so y * z = x, which makes z the quotient; `cConst`
creates a connector and pins it with a `constant` box. `celsiusFahrenheit`
then reads as the book's expression over those combinators.

Why (multiply before dividing, because values are `Long`): the book's
literal shape is (9/5) * x, and with exact rationals that is what you would
write. Here `cDiv(cConst(9L), cConst(5L))` asks the multiplier to infer
9/5 the moment both constants exist, and Long division truncates it to 1;
the book's session would then turn 25 into 57. Arranging the expression as
cPlus(cDiv(cMul(cConst(9L), x), cConst(5L)), cConst(32L)) computes 9 * x
first, so the one division the network performs is 225 / 5 forward and
900 / 9 backward -- both exact, and the book's 25 -> 77 and 212 -> 100
sessions hold in both directions. The statement says this to the reader;
the test pins the truncation itself, so the caveat cannot silently rot.

What the tests say: `E3_37Test.kt` runs the book's session through the
expression-style network (25 gives 77, then a forgotten network takes
f = 212 back to c = 100), composes all four arithmetic combinators over
constant connectors, and pins `cDiv(9, 5)` to 1 as the documented Long
behavior. A combinator that wired its multiplier or adder with swapped
arguments would still compile but would fail the backward session, since
the inference directions are exactly what the argument order chooses.

Class: `T`.

Deviation: the converter multiplies by 9 before dividing by 5, instead of
the book's (9/5) * x; this is forced by Long arithmetic and documented in
the exercise statement and above.
