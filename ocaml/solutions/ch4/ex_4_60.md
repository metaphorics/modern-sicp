# Exercise 4.60: lives-near pairs, duplicates and a deduplicated formulation (translate)

The book's `lives-near` rule is used as stated, on the Microshaft address
assertions. The pair query `(lives-near ?person-1 ?person-2)` lists each pair
of neighbors twice because the two `address` conjuncts are independent: binding
`?person-1` to Alyssa and `?person-2` to Cy is one solution of the conjunction,
and the swapped binding is another, and both survive `(not (same ...))`. The
run also shows why the pair order interleaves across towns: the evaluator's
`stream-flatmap` interleaves the per-frame streams, so the matches of all nine
first-person frames come out round-robin rather than town by town: hence the
`(Fect Cy D)`-first occurrence of the Hacker/Fect pair before the
`(Hacker Alyssa P)`-first one.

For the deduplicated formulation the classic answer orders each pair by a name
comparison through `lisp-value`; the base system's `lisp-value` resolves its
predicate only in the section 4.1 primitive table, which installs no symbol or
string comparison, only the integer `<`. The edition's `lives-near-unique`
therefore orders each pair by salary (`(lisp-value < ?salary-1 ?salary-2)`),
which keeps exactly one of the two orders and also excludes the self-pair the
book's `not (same ...)` clause removed. Deliberate deviation: the ordering key
is salary, not the name; two same-town neighbors with equal salaries would need
the name comparison a real driver installs.
