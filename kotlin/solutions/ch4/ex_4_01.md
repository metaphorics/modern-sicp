# Exercise 4.1: operand evaluation order in list-of-values

## Approach

The Scheme text cannot tell which order `list-of-values` gives because the
order belongs to the host's `cons`. Kotlin closes the question differently:
the host's own application order is fixed, operands left to right, so the
base evaluator's `listOfValues` maps the operands in order and the order is
definite. The exercise therefore rewords (the map's A-class reword): make
the order a property of the evaluator's own code by writing the operand
walk explicitly, then write the right-to-left version to see what the host
had been deciding.

The solution keeps the base `listOfValues` (left to right, the host's
order) and adds `RightToLeft`, a subclass whose operand walk is one
`foldRight`: operands evaluate last-first, each value consed onto the
already-evaluated rest, so the argument list the operator receives is
identical while the evaluation order inverts. The probe is the book's own
device, `(cons (note 1) (note 2))` with `note` pushing onto a recorded
list, run through the driver-transcript convention.

## Map class

`A` (map row 4.1: Kotlin `A: host fixes order, reword premise`). The
statement is reworded in `kotlin/book/ch4/4.1.texi` to name the host's
fixed left-to-right order and why the exercise still matters.

## Deviation

None. Kotlin has no evaluation-order ambiguity to expose; the reworded
statement asks for both explicit walks, and both are implemented.

## Answer

- Base evaluator (left to right): `(cons (note 1) (note 2))` prints
  `(1 . 2)` and `order` reads `(2 1)`; `(2 1)` is `note 2` pushed after
  `note 1`.
- `RightToLeft`: same transcript except `order` reads `(1 2)`.
- Pin: `leftToRightTranscript() == "(1 . 2)\n(2 1)\n"` and
  `rightToLeftTranscript() == "(1 . 2)\n(1 2)\n"`; the cons receives the
  same values either way (first transcript lines equal).
