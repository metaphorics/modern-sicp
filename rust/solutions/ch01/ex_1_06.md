# Exercise 1.6: Eva's `new-if`, an ordinary function with ordinary eager arguments

## Approach

Eva's claim is that `if` is unnecessary as a special form, because an
ordinary procedure built from `cond` behaves the same way. As a plain
function, `new_if` does return the right value:

```rust
pub fn new_if<T>(predicate: bool, then_clause: T, else_clause: T) -> T {
    if predicate { then_clause } else { else_clause }
}
```

`new_if` is generic because the book's untyped `new-if` is exercised two
different ways in this section: with plain numbers directly (to show it
computes the right answer) and, below, plugged into a `sqrt-iter` that
operates on `f64`. A single monomorphic signature could not serve both
call sites; the type parameter `T` is exactly as permissive as Scheme's
lack of static types is here, and each call site still gets full
type-checking at its own instantiation.

## Alyssa's rewritten `sqrt-iter`

```rust
pub fn sqrt_iter_new_if(guess: f64, x: f64) -> f64 {
    new_if(
        good_enough(guess, x),
        guess,
        sqrt_iter_new_if(improve(guess, x), x),
    )
}
```

This function is written but never called by the test: calling it would
hang, or overflow the stack, exactly as the exercise predicts.

## Why it diverges

`new_if` is an ordinary function, and Rust (like Scheme's applicative
order) evaluates a function's arguments before the call. The third
argument here is `sqrt_iter_new_if(improve(guess, x), x)`, a recursive
call; evaluating *that* argument requires evaluating `new_if`'s third
argument in the next stack frame, and so on, forever, before `new_if` is
ever entered and gets a chance to look at `predicate` and pick a branch.
The special form `if` (and Rust's own `if`) is different: `if` is syntax,
not a procedure call, and it evaluates only the taken branch. This is the
same lesson as exercise 1.5, applied to Alyssa's specific program: `new_if`
cannot be a plain procedure and still short-circuit, because plain
procedures do not get to defer evaluating their own arguments.

## Test

`new_if(2 == 3, 0, 5) == 5` and `new_if(1 == 1, 0, 5) == 0` confirm `T =
i64` works and picks the right branch. A further check with a
side-effecting closure argument confirms both `then_clause` and
`else_clause` are evaluated exactly once each before the call (`evaluated`
reaches `2`), which is the eager-argument behavior the exercise is about.
The test also type-checks `sqrt_iter_new_if: fn(f64, f64) -> f64` without
calling it.
