# Exercise 1.20 (replaced)

This edition replaces the original exercise, which asked how many times
Scheme's normal-order (lazy, substitute-then-evaluate) evaluation rule
would call `remainder` while computing `gcd(206, 40)`, compared with
applicative (eager) order. Rust has one evaluation order, eager, so the
eager count is the one the code can measure directly: instrumenting `gcd`
shows it calls `remainder` exactly 4 times, once per reduction
`gcd(206,40) -> gcd(40,6) -> gcd(6,4) -> gcd(4,2) -> gcd(2,0) = 2`.

The normal-order count is still worth deriving by hand, because it is the
same substitution-model reasoning the section teaches and is where the
original exercise's "18" comes from. Under normal order, each argument is
an unevaluated expression that gets substituted whole and is evaluated
only when a test needs its value; a `remainder` inside an argument that
never gets evaluated is never counted, but one that does get evaluated is
recomputed from scratch every time it is needed, since nothing memoizes
it. Writing out the growing argument expressions:

```
gcd(206, 40)
gcd(40, r(206, 40))                                       ; test: 1 call
gcd(r(206, 40), r(40, r(206, 40)))                         ; test: 2 calls
gcd(r(40, r(206, 40)), r(r(206, 40), r(40, r(206, 40))))   ; test: 4 calls
... one more step ...                                      ; test: 7 calls, then true
                                                             ; return: 4 calls
```

Summing the calls spent on each test (`0 + 1 + 2 + 4 + 7`) and the final
`4` needed to produce the returned value gives `18`, matching the classic
answer: normal order redoes the same reductions again because it never
remembers a value once computed, while eager evaluation computes each
remainder exactly once. The map class is `R`: the exercise is inherently
about Scheme's two evaluation orders, so this edition keeps the number and
asks for the one evaluation order Rust has, with the normal-order
comparison moved into this rationale instead of the code.
