# Exercise 3.45: double serialization deadlocks

## Approach

Louis's account protects its deposits and withdrawals with the same
serializer it hands out. The solution builds that account on the
section's halt-aware hand-rolled serializer and runs the text's
`serialized-exchange` shape: acquire the first account's serializer,
then the second's, then run an exchange body whose deposit enters the
first account's serializer again. Two such exchanges over disjoint
account pairs run on two real threads; each process blocks on its own
already-held serializer with nobody else involved, the harness waits
until both are inside, and the run handle ends the spin so the
deadlock is proven rather than hung. Both processes answer nothing:
each waited forever on the one serializer it already held, which is
why a serializer has no notion of its owner.

## Map class

`T`. Louis's redefinition and the deadlock question are the
statement's own.

## Deviation

The deadlock demonstration needs an escape hatch a standard mutex
block does not offer, so Louis's account uses the section's
`BookSerializer`, whose acquire polls the run handle; the semantics of
the bug are unchanged. Disjoint pairs isolate Louis's self-deadlock
from the opposite-order crossing, which is the text's separate
scenario and exercise 3.48's subject.
