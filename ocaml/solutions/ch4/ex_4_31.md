# Exercise 4.31 — lazy and lazy-memo parameter declarations (translate)

The map class is `T`. The statement's extension is implemented at the
edition's syntax boundary: the driver's reader cannot parse
`(b lazy)` inside a parameter list, so the "new syntax procedures" the
statement asks for are a datum-level parse — the extended `define` is
read as a quoted datum and its parameter list becomes a list of
declarations `{ name; mode }` over the typed AST, with `a` strict,
`(b lazy)` delayed without memoization, and `(d lazy-memo)` delayed
through a host `Lazy` cell. The body lifts back into `Ast.expr` by a
small datum-to-expression mapping (self-evaluating items, symbols,
`quote`, `if`, applications).

Application of an annotated compound procedure binds per declaration:
strict parameters are forced at the call, `lazy` parameters are bound to
unmemoized thunks, `lazy-memo` parameters to memoized ones; ordinary
definitions keep Scheme's strictness, which is the upward compatibility
the statement demands. The declarations travel beside the procedure
value in a table keyed by physical identity, the same shape the 4.1
analyzer uses for procedure bodies.

The demonstration: a `lazy` parameter never forced saves an armed
`(/ 1 0)` (`(pick (car '()))` answers `taken`); the four-way declaration
forces the strict parameters at the call, runs the `lazy` parameter once
per use and the `lazy-memo` parameter once in total, and the counting
identity reads 5; the same armed arm under `lazy` alone runs twice where
`lazy-memo` runs once (counts 2 against 3).

Sample: `ex_4_31 ()` answers
`["ok"; "taken"; "ok"; "(1 5 5 4 30 30)"; "5"; "ok"; "(10 10)"; "2";
"ok"; "(10 10)"; "3"]`.
