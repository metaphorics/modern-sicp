# Exercise 3.7: a joint account shares one balance

## Approach

`make_joint` first asks the existing account to `authorize` the old password
(exercise 3.3's mechanism), which either answers the complaint or hands out
another name for the same balance object; `PasswordAccount::joint` then wraps
that shared name under the new password. The sharing is the hard spot the
section's idiom note names: two password front-ends cannot each own a copy of
the balance, so the balance must live behind the `Rc` the section's
`make_account` already uses. The test shows a withdrawal through the joint
front-end visible through the original, refusal on a wrong old password, and
the aliasing made explicit.

## Map class

`T`: the statement translates directly.

## Deviation

The map's sketch said "returns `Box<dyn FnMut>` for wrappability"; the landed
solution returns a second `PasswordAccount` over the shared `Rc<Cell<i128>>`
instead, which is wrappable (it clones) without erasing the request/reply
types, and it keeps the aliasing check available.
