# Exercise 5.25: normal-order evaluation in the controller

The plan, made before the controller was written:

1. Thunks are machine words (`Thunk` of expression and environment),
   built by one operation, `make-thunk`, so the base word type carries
   the laziness and nothing else does.
2. Bindings of thunked operands go through the shared environment with
   placeholder symbols: `extend-environment` binds each parameter to a
   reserved symbol no object symbol can spell and records the symbol's
   thunk in a side table; `lookup-variable-value` answers the recorded
   thunk when it finds a placeholder. Frames keep their shape, so
   `define-variable!` and `set-variable-value!` work unchanged.
3. The controller changes in exactly three places: the argument loop
   makes a thunk per operand and adjoins it (no saves, no recursion,
   which is the laziness); `ev-variable` forces a thunked binding the
   first time the variable is read and memoizes by storing the forced
   value over the placeholder with `set-variable-value!`;
   `primitive-apply` forces any thunks left in `argl` before the
   primitive sees them, saving `proc`, `unev`, `argl`, and `continue`
   around each nested evaluation.

The code follows the plan: `lazy_argument_loop`,
`lazy_ev_variable`, and `lazy_primitive_apply` are the three replaced
fragments; everything else is the base controller.

One deviation is recorded: memoization is per binding, not per thunk
object. The book memoizes by mutating the thunk pair, which the
edition's immutable values cannot do; a thunk aliased into two
variables is recomputed. Every session here observes single-variable
references, where the two agree.

`ex_5_25 ()` pins the three proof groups: `(factorial 5)` still answers
`120` under normal order; `(always-42 (car '()))` answers `42`, where
the strict evaluator would crash on the never-used argument; and
`(use-twice (bump))` answers `(1 1)` with `count` left at `1`, so the
thunked `(bump)` ran once, not once per reference.
