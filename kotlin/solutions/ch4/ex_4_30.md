# Exercise 4.30: forcing in `eval-sequence`

## Approach

The edition's rule, stated: sequences keep the text's behavior; non-final
expressions evaluate, only demand sites force. The rule lives in two
places because a body sequence and an explicit `begin` are the same thing
in this evaluator: the lazy evaluator's body prefix and the base `begin`
clause. [CySequenceLazy] forces both, overriding the body-prefix seam and
the `begin` clause with `actual-value`.

Part (a): Ben is right about `for-each` because its non-final expression
`(proc (car items))` is an application whose own demand sites force (
`newline` and `display` are strict primitives), so the elements print
under the text's rule unchanged. Part (c) is the same fact read from the
other side: Cy's forcing adds nothing, and the transcript pins the
identical output.

Part (b): `(p1 1)` is `(1 2)` under both; `set!`'s own evaluation forces
the `cons` arguments, so the mutation happens without sequence forcing.
`(p2 1)` is the pin that separates the rules: `p`'s non-final body
expression `e` evaluates to the delayed `set!` argument; the text's rule
leaves the thunk unforced, so `x` stays 1; Cy's rule forces `e`, the
mutation runs, and `x` reads `(1 2)`.

## Map class

`T` unchanged; the pins match the siblings (`(1 2)`/`1` versus
`(1 2)`/`(1 2)`; identical `for-each` output).

## Answer

From the actual runs (`E4_30Test` pins all four transcripts):

- `for-each`: => newline, `57`, `321`, `88`, then `done`, identical
  under both rules.
- Text rule: `(p1 1)` => `(1 2)`, `(p2 1)` => `1`.
- Cy's rule: `(p1 1)` => `(1 2)`, `(p2 1)` => `(1 2)`.

The edition's verdict, as in the committed siblings: keep the text's rule
for the language, implement Cy's variant where a program needs the
forcing.
