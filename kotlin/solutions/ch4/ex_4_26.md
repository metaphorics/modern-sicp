# Exercise 4.26: unless as a special form versus a procedure

## Approach

Ben's side: `unless` as a derived expression. The rewrite lives in guest
code over the kernel's sealed family -- the three-arm application lowers to
`GIf(condition, exceptional, usual)` -- so the untouched arm never
evaluates, and the derivation is syntax: no binding carries the name.
Alyssa's objection is pinned at the kernel plane: using the name as a
value fails, and the kernel's application guard fires before any argument
effect runs.

Alyssa's side: under the lazy experiment `unless` stays an ordinary
procedure whose operands are delayed thunks, so it composes. A
higher-order caller takes the procedure as a value, the unchosen arm's
thunk is never forced, and the same call through the caller answers the
chosen arm.

## Map class

`T`; the statement keeps both positions. The failure plane changes: the
old unbound-variable wording becomes the kernel's null-means-error answer
(the represented program's fault, never a source diagnostic).

## Deviation

The derived-form story is told over the sealed syntax family in guest code
instead of a host parser hook; the value-use failure renders as `error`
(the kernel renderer) rather than an engine wording pin.

## Answer

- `unlessDerivedTranscript() == "42\n"`: the derived `unless` answers the
  chosen arm; the plane probe prints `42` then the unchosen arm's counter
  `0` (`"42\n0\nerror\n0\n"`), proving both that the arm never evaluated
  and that the guarded call ran no argument effect.
- `unlessDerivedValueUseTranscript() == "error\n"`: the name is not a
  value.
- `unlessLazyProcedureTranscript() == "42\n"`,
  `unlessLazyMappedTranscript() == "[42, 7]\n"`,
  `unlessLazyApplyTranscript() == "7\n"`: the procedure composes as a
  value, and none of these runs forces the `1 / 0` arm (any forced arm
  would fault the run).
