## Exercise 2.97: reducing to lowest terms, system-wide

Approach: [reduceTerms] is the book's three-step reduction: compute
`g = gcdTerms96(n, d)` (exercise 2.96), integerize both `n` and `d` by
`g`'s leading coefficient raised to `1 + max(O_n, O_d) - O_g`, divide
both by `g`, then strip the pair's own remaining integer content.
[reducePoly] checks the shared variable and reattaches it; the book's
own [reduceIntegers] does the same job for the integer package;
[reduce] is the generic dispatcher between the two. Finally,
[installReducedRationalFunctionPackage] rewires exercise 2.93's package,
passing a `makeRat` that calls `reduce` (falling back to the unreduced
pair only if `reduce` itself cannot dispatch), so every operation of
the package now answers in lowest terms. `ex_2_97` reproduces the
book's `rf1 = (x+1)/(x^3-1)`, `rf2 = x/(x^2-1)`, sums them, and shows
the reduced answer `(x^3+2x^2+3x+1)/(x^4+x^3-x-1)`.

Class: A, per the map; rewiring the package's constructor through a
generic `reduce` operation, shared with the integer level via one
dispatcher, is this edition's way of making "install this in the system
as a generic operation" concrete.

Deviation: two bugs surfaced while proving this exercise, both fixed
here rather than in exercise 2.96's own file. First, Euclid's algorithm
fixes a polynomial GCD only up to sign, and `gcdTerms96` can return
either sign depending on which division steps happen to land negative;
left unnormalized, `reduceTerms`'s quotient and its divisor's quotient
both flip sign together (mathematically the same fraction, but not the
book's printed sign), so `reduceTerms` now normalizes `g`'s leading
coefficient positive before dividing. Second, this bug was only exposed
once exercise 2.93's `add` handler was corrected to cross-multiply (see
that file's own deviation note); the two fixes together are what make
`ex_2_97`'s reduced sum match the book's printed answer exactly.
