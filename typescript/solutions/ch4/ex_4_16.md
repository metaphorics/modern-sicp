# Exercise 4.16: scan out internal defines

## Approach

Three parts. (a) Lookup answers `tdz-access` when it finds an
uninitialized cell, so reading a name before its initializing write is
an error rather than a silent wrong value — `undefined` cannot stand in
for "not yet assigned" without losing the distinction the exercise
asks about. (b) `scanOutDefinitions` rewrites a body with no
declarations remaining: every internal `const`/`let`/function
contributes its name to a set pre-bound with `addUninitialized` and its
initializing write at the declaration's position, and the remaining
statements follow; a declaration-free body is returned unchanged. (c)
The scan is installed in the procedure constructor, not in the body
reader: the rewrite then runs once when a closure is created instead of
on every application that reads the body.

## Numbers

`scanOutDefinitions` over `const a = 1; const b = 2;` keeps the names
`["a", "b"]` and the two writes followed by the remaining statements;
a define-free body compares equal to itself after scanning. The
mutually recursive internal `even?`/`odd?` answers `false` for `7` and
`true` for `8` under the scanned application — the pre-bound names are
exactly what makes the mutual recursion resolvable. The program
`const a = b; const b = 1; return a;` fails with `tdz-access` naming
`b`: the first write reads `b` while `b` is still uninitialized. The
scan-at-creation pin: three applications of one procedure run exactly
one scan.

## Class and deviations

Translated row. Deviations: the pre-binding is the engine's real
uninitialized cells rather than a `'*unassigned*` marker value, which
is why part (a) is the engine's own TDZ fault; and the transformation's
writes are assignment statements in place of the book's `set!` forms in
a generated `let`, since the pre-binding already supplies the let's
frame semantics.
