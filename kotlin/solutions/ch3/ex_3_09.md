## Exercise 3.9: two factorials, two frame shapes

Approach: both versions live in `E3_09.kt`. The recursive `factorial`
does no work on the way down; it opens a frame binding its own `n`,
calls itself with `n - 1`, and only multiplies once the base case
returns, so the deepest point of `factorial(6)` has six frames stacked,
each waiting on the one below it to finish before it can compute its
own answer (`6 * (5 * (4 * (3 * (2 * (1)))))`). The iterative `factIter`
carries `product` and `counter` as parameters instead: at the deepest
point of `factorialIter(6)` there is still only one frame, because
`factIter`'s self-call is the last thing its body does and the `tailrec`
mark makes the compiler rewrite that self-call as a loop rather than a
new stack frame -- the frame is reused, not stacked.

Diagram, in the book's own style (one box per environment, arrows to
the enclosing one):

```
factorial(6)              factIter(1, 1, 6)
  n: 6  ---> global          product: 1, counter: 1, maxCount: 6  ---> global
  n: 5  ---> global          (loop: product: 1,  counter: 2)  ---> global
  n: 4  ---> global          (loop: product: 2,  counter: 3)  ---> global
  n: 3  ---> global          (loop: product: 6,  counter: 4)  ---> global
  n: 2  ---> global          (loop: product: 24, counter: 5)  ---> global
  n: 1  ---> global          (loop: product: 120,counter: 6)  ---> global
                             (loop: product: 720,counter: 7)  ---> global
```

The left column is a real stack: six frames, live at once, each pointing
to the global environment where `factorial` was declared. The right
column is one frame whose `product` and `counter` are reassigned on each
iteration of the loop the compiler generated; nothing below the top line
is ever live at the same time as anything above it.

Class: `R` (the exercise is about Scheme's environment diagrams; this
edition replaces it, keeping the number, with the Kotlin question of
what `tailrec` changes about the frame count).

Footnote: the book's claim that the interpreter can run `fact-iter` in
constant space needs an interpreter with a proper tail-call guarantee
(discussed in 5.4). Kotlin's JVM bytecode has no such blanket guarantee
for ordinary recursive calls: only a function the compiler accepts as
`tailrec` gets the loop rewrite, and only for its own direct
self-recursive calls in tail position. `factorial` above is not tail
recursive (the multiplication happens after the self-call returns), so
marking it `tailrec` would be a compile error ("a function is marked as
tail-recursive but no recursive call is found" or, if a call exists but
is not in tail position, the mark is simply not honored and the
compiler warns that the function does not exhibit tail recursion).
Exercise 3.9a makes this difference in frame count observable rather
than just diagrammed.

Deviation: none.
