# Exercise 4.3: data-directed dispatch in eval

## Approach

The special-form dispatch becomes a table keyed by the operator symbol
name, one operation per form: quote, if, set!, define, lambda, begin, and
cond, each wrapping the module's helpers. The car of a compound expression
is its type, as in the data-directed differentiation of exercise 2.73.
Self-evaluating expressions and variables carry no tag, so they bypass the
table; a pair whose car is not installed falls through to the application
path. The spine's `OpTable` stores `Primitive` operations of evaluated
argument lists, so the table is built per environment through an adapter
that guards the expression out of the stored argument list, memoized in a
WeakMap.

## Numbers

`(define (square x) (* x x))` gives `ok` and `(* (square 6) (square 7))`
is `1764`. `(quote (a b c))` is `(a b c)`. `(cond ((= 1 2) 'yes)
(else 'no))` is `no`. After `(define n 1)`, `(set! n 5)` is `ok` and `n`
is `5`. `((lambda (x) (* x 2)) 21)` is `42`, `(begin 1 2 3)` is `3`,
`(list 1 2 3)` is `(1 2 3)`, and a cond nested in a defined body
classifies `-5` as `neg`.

## Class and deviations

Translated row. Deviation: the book's table operations take the
expression and the environment, while the spine's OpTable is typed for
primitives over argument lists only, so the installed operations are
wrapped per environment instead of stored raw; the put/get shape and the
keyed dispatch are unchanged.
