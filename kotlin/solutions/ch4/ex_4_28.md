# Exercise 4.28: forcing the operator

## Approach

Application dispatches on the procedure value in the operator position,
so what sits there must be an actual procedure, not the thunk an argument
would be. In `id(::add)(2, 3)` the operator expression evaluates to
`id`'s parameter, which the application delayed; the lazy experiment
forces the operator before application (a pinned invariant), the call
dispatches on `add`, and the answer is 5.

The counterfactual -- applying the thunk itself without forcing -- cannot
survive source typing: `op` holds a `Thunk`, and calling it is a type
error, so the checker rejects the program before any guest effect. That
is the failed-admission-before-effect boundary in its sharpest form: the
untyped lazy evaluator would have trapped at run time with a
not-a-procedure fault; the typed surface never runs the program at all.

## Map class

`T`; the objective (why the operator must be forced) is unchanged. The
counterfactual's observable moves from a runtime not-applicable fault to
an admission rejection, because the typed surface cannot express an
unforced operator call.

## Deviation

The counterfactual transcript renders the rejection category instead of
an engine wording pin; if the rejection occurs before effects, the
`before` effect in the counterfactual probe will never run.

## Answer

- `forcedOperatorTranscript() == "5\n"`: the operator forced, the call
  dispatches on the `add` function.
- `unforcedOperatorTranscript() == "Error: <rejection category>\n"`: the
  call is rejected at admission; no effect of the probe runs.
