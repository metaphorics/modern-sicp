# Exercise 4.79: environments instead of renaming (translate)

Rule application becomes a procedure call. Each application gets a
layer of its own with three parts: `params`, the conclusion's
parameter bindings, fixed for the application; `local`, what the
body's matches add; and the parent chain, the caller's bindings.
Lookup reads local, then params, then walks outwards, so a recursive
application's variables shadow their same-named ancestors inside the
call (the discipline renaming achieves by freshening names). Variables
the rule owns but no binding resolved stop the walk: the body never
reads the caller's same-named variable, which is exactly the
name-conflict renaming exists to prevent. Parameters passed a
*variable* argument are aliased (share): the pair (param, caller var)
is chased on every read and write, so a bound argument contributes its
value and an unbound one is constrained by the body's matches: the
environment form of renaming's pointer bindings, with the write
landing at the layer that owns the caller's variable and each
intermediate layer re-linked to the new ancestor. On return the layer
is squashed into its parent: the body's caller-visible bindings join
the parent's locals and the parameters vanish, as a call's frame is
discarded. The match, binder, and instantiate are re-owned over
scopes; the data base, index, and stream combinators are the
base evaluator's, and the evaluator mirrors its clause structure, so answer
order is the stream system's.

The demo pins equivalence with the renaming engine on the recursive
`outranked-by` rule over Microshaft (including the salary join whose
bound `?staff-person` must flow into the rule through the chain),
asserting identical answer lists, order included. The exercise's
open-ended reaches (block-structured rule environments, deduction in a
supposed context) are beyond this edition: it implements the
scoped-frame core and its renaming equivalence.
