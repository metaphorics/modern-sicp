# Exercise 1.20: counting remainder calls in the eager gcd

## Approach

Replace the `%` in the section's `gcd` loop with a `remainder` helper
that bumps a counter, then reduce `gcd(206, 40)`. The reduction chain is
`(206, 40) -> (40, 6) -> (6, 4) -> (4, 2) -> (2, 0)`: one remainder per
reduction, four in all.

## Numbers

`tracedGcd(206, 40)` returns `{ value: 2, remainderCalls: 4 }`. A
thunk-level simulation of the book's normal-order trace - each argument
carried as a closure, forced only when a test needs it - forces the
remainder expression `18` times on the same input, because the deferred
remainder is substituted unevaluated into every later reduction and
forced once per occurrence. Eager evaluation computes each remainder
exactly when it is needed and never again: four.

## Class and deviations

Replaced row (the fixed signpost stands in the statement): no host in
this book evaluates lazily, so the normal-order half of SICP's exercise
cannot be performed here. The replacement keeps the section's lesson -
evaluation order changes the cost, not the answer - and the rationale
carries the normal-order count as simulation data rather than code the
edition ships. The eager count is asserted in the test.
