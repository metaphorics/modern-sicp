# Exercise 5.23: derived expressions via transformer operations

The subset has no `cond`; its multi-way conditional is the literal
`match`, a match whose cases are literals, a variable, or the wildcard,
as in `match n with 0 -> "zero" | 1 -> "one" | _ -> "many"`. The
exercise's cheat is taken literally for it and for the parallel `let`:
`cond->if` and `let->combination` are machine operations, and the
dispatch grows two tests, `cond?` and `let?`, ahead of the base tests.
Each new entry rewrites `exp` and re-enters `eval-dispatch`, so the
rest of the controller never knows the forms existed. A match with any
other pattern is not the subset's `cond` and still reaches the base
`ev-match`.

`cond->if` builds a function of the scrutinee applied once to it, whose
body is the book's chain of `if`s testing equality with each literal.
The scrutinee's parameter name contains a space, so no guest variable
can capture it; a variable case binds the scrutinee by a second
application. The book's two edge answers do not carry over: a clause
without actions and a `cond` with no true clause cannot be written,
because admission requires every match to be exhaustive. The final
case therefore needs no test, which is why the Boolean match
`match 3 < 2 with true -> "yes" | false -> "no"` answers `no` with one
comparison. `let->combination` is the book's: a function of the bound
names applied to the right-hand sides.

`ex_5_23 ()` pins the answers `zero`, `one`, `many`, `no`, `14` (the
variable case), and `6` (the `let`), and then the price of the
derivation: `classify 7` costs 26 pushes and 368 instructions through
`cond->if`, against 8 pushes and 127 instructions through the base
`ev-match`. The instruction counts include the added dispatch tests,
which cost two instructions at every `eval-dispatch` arrival; pushes
carry no such overhead, so the 26-to-8 push gap is the transformer's
own price.
