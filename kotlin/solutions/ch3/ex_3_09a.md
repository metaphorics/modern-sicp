## Exercise 3.9a: making the frame difference of exercise 3.9 measurable

Approach: `E3_09a.kt`'s `runOnSmallStack` runs a `() -> Long` body on a
`Thread` built with an explicit `stackBytes` stack size (the four-argument
`Thread(ThreadGroup?, Runnable, String, Long)` constructor is the only
public JVM constructor that lets a caller choose the stack size), catches
`StackOverflowError` around the run, and reports `StackOutcome.Overflow`
or `StackOutcome.Completed(value)`. `runRecursive` and `runTailrec` apply
it to `factorial` and `factorialIter` from exercise 3.9.

Why a 64&nbsp;KiB stack and `n = 100000`: exercise 3.9's recursive
`factorial` needs one live frame per pending multiplication, so
`factorial(100000)` needs about 100,000 simultaneously live frames; even
at a generous few hundred bytes per frame that is tens of megabytes,
far past 64&nbsp;KiB, so the recursion is certain to die with a
`StackOverflowError` on any JVM. `factorialIter`'s self-call is rewritten
by `tailrec` into a loop, so its frame count stays at one (plus whatever
`runOnSmallStack`'s own call added) regardless of `n`; 64&nbsp;KiB is
easily enough for that one frame, so the run always answers, and the
`Long` multiplication (deterministic even once it wraps past
`Long.MAX_VALUE`, since Kotlin's `*` on `Long` is unchecked
two's-complement arithmetic) completes in a fraction of a second either
way. `E3_09aTest.kt` checks both extremes: the overflow at `n = 100000`,
that the `tailrec` run at the same `n` is a `Completed` (its exact wrapped
value is not asserted, since pinning an overflowed constant would test
arithmetic wraparound rather than the frame behavior this exercise is
about), and that both versions agree on the ordinary value 120 at the
small case `n = 5`.

What the `StackOverflowError` says about the recursive version's
structure: it says the chain of enclosing environments got too long
before the base case was reached -- exactly the six-deep (or, here,
100,000-deep) stack of frames exercise 3.9 asked readers to draw, made
observable instead of just drawn. Every one of those frames is real,
live, and holding its own `n`, waiting for the frame below it to return
before it can multiply; that pile of waiting frames is what a small
stack cannot hold.

Why no `n` can kill the `tailrec` version: the compiler's rewrite means
`factIter`'s "recursive call" never actually recurses at the bytecode
level -- it becomes a jump back to the top of one loop, reusing the same
frame's slots for the next `product` and `counter` rather than opening a
new frame enclosed by the old one. There is only ever one frame for the
whole call, so the frame count is a constant, independent of `n`; the
stack a `tailrec` function needs is the stack one ordinary function call
needs, no matter how many times the loop turns.

What Kotlin checks before accepting `tailrec`: the compiler verifies
that every call to the function from within itself is a *tail* call --
the last action of the code path that contains it, with nothing left to
do with its result (no `n * factorial(n - 1)`, which multiplies *after*
the call returns). If the function makes no self-call at all, or if
every self-call sits somewhere that still has work to do afterward
(inside a `try`, or as here in `factorial`, as the left operand of a
multiplication), the compiler does not perform the rewrite and instead
warns that the function is "not tail recursive"; under this project's
`allWarningsAsErrors`, marking `factorial` above as `tailrec` would fail
the build outright rather than silently keep the ordinary recursive
frame-per-call behavior.

Class: this is the section's one chosen tailored addition (map row 3.9,
idea "stack frames you can measure: recursive versus tailrec factorial
on a small stack"), recorded as `chosen: kotlin` on that row.
