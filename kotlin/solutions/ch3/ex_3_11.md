## Exercise 3.11: where a message-passing account keeps its state

Approach: `makeBankAccount` in `E3_11.kt` opens one call frame per call,
binding `balance`; that frame's local `var b` is the account's state
cell, and the returned `object : BankAccount` expression's two overrides
capture it. There are no local `fun`s standing in for the book's
internal `withdraw`/`deposit`/`dispatch` definitions here; the
object's own methods play that role directly, so the "internal
definition" of this section shows up as the object's member functions
rather than as separate local functions calling each other.

Trace of `acc = makeBankAccount(50L)`: the call opens frame E1, binding
`balance: 50` and then `b` (the local `var`, initialized from
`balance`). The returned object's `withdraw` and `deposit` methods both
capture E1. `acc.deposit(40L)` opens a fresh frame binding `amount: 40`
whose enclosing environment is E1; the method body finds `b` there,
adds 40, and returns the new value, 90. `acc.withdraw(60L)` similarly
opens a frame enclosed by E1, finds `b` is now 90, and returns
`Either.Right(30)`.

Where the local state lives: in `b`, the one captured `var` of E1,
not in the `BankAccount` interface, not in the `makeBankAccount`
function itself (which only runs once per account and then returns),
and not in the object's class, which has no state of its own.

How the two accounts' states stay distinct: `acc2 = makeBankAccount(100L)`
is a second call to `makeBankAccount`, so it opens a second, independent
frame E1', with its own `b`. `acc`'s methods capture E1; `acc2`'s
methods capture E1'. Nothing connects the two frames, so a withdrawal
from one account can never touch the other's balance:
`E3_11Test.kt`'s "a second account keeps its own state" test drives
both accounts through independent sequences of calls and checks neither
affects the other.

Which parts are shared: `acc` and `acc2` are built from the same
anonymous `object : BankAccount` expression, so the JVM compiles their
`withdraw` and `deposit` method bodies exactly once; both accounts'
methods are the same compiled code, executed against two different
captured `b` cells. `E3_11Test.kt` observes this two ways: `(acc ===
acc2)` is `false` (they are not the same object: distinct identity,
distinct state), while `acc::class.java` equals `acc2::class.java` (the
same anonymous class, hence the same compiled method bodies), which is
the one part of the sharing an ordinary Kotlin program actually can
observe. What it cannot observe (whether the JVM keeps one copy of
the bytecode in memory or several) is an implementation detail below
the language, exactly as the book's own footnote says of Scheme's
`W1`/`W2` example.

Class: `R` (the exercise is a Scheme environment-diagram question; this
edition replaces it with the Kotlin questions of where state lives, how
two accounts stay independent, and what `===` versus `::class.java` can
tell you about the sharing).

Deviation: none.
