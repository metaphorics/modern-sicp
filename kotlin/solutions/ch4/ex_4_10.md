# Exercise 4.10: self-evaluating syntax -- defun and fun at the reader level

## Approach

The Scheme text asks for a language whose syntax differs from the
metacircular evaluator's, and warns that any evaluator written by hand
depends on the reader of the host. This host takes the warning literally
and changes the syntax at the data level, before the parser runs:
`syntaxize` is a `Value`->`Value` transform over the read datums, mapping
`(defun name (params...) body...)` to the procedure-defining `define`
sugar and `(fun (params...) body...)` to `lambda`. The rewrite is
structural and depth-first -- operands, parameter lists, and bodies all
re-pass through `syntaxize` -- so a `fun` nested in a `defun` body
arrives at the parser as a `lambda` inside a `define`. A malformed
`defun`/`fun` fails the shape checks and passes through untouched, which
makes `defun` an ordinary unbound head at eval time: the same program
with and without the transform is the honest contrast the exercise
draws. The demo runs `(defun cube (x) (* x x x))`, calls it, and defines
`twice` whose body carries a nested `fun`, then applies the composition.

## Map class

`T` (the Kotlin edition statement keeps the exercise as written; the
transform plays the role of redefining the reader the book assumes).

## Deviation

None. The exercise's "syntaxize" is answered at the reader level, the
level the exercise names; the evaluator itself is untouched.

## Answer

- `syntaxize(readDatum("(defun cube (x) (* x x x))"))` prints
  `(define (cube x) (* x x x))`; `syntaxize(readDatum("(fun (x y) (+ x y))"))`
  prints `(lambda (x y) (+ x y))`.
- With the transform, the demo program prints `343` (`(cube 7)`) and
  `512` (`((twice cube) 2)`, the nested `fun` composing `cube` with
  itself): transcript `"343\n512\n"`.
- Without the transform, the run stops on the first form:
  `"Error: unbound variable: defun\n"`.
