# Exercise 4.2: dispatch order and call-prefixed applications

## Approach

`ApplicationsFirst` runs the application clause before the special-form
clauses: `(define x 3)` evaluates as an application of the (unbound)
operator `define` -- the flaw Louis missed, answered typed as
`Unbound("define")`. This host's parser classifies definitions and
assignments into typed `DefineE`/`SetE` nodes before eval sees them, so the
reordering is a demotion: `step` rebuilds the two node shapes as the pairs
the application clause catches and then applies them, which also demotes
`(set! x 3)` from the base's `Unbound("x")` to `Unbound("set!")` -- the
order question made observable. `CallSyntax` answers part (b): one `step`
clause strips a `(call f x)` application to `(f x)` before the base clauses
run, re-entering at every depth, so nested `(call ...)`s strip too while
the special forms and bare combinations keep working.

## Map class

`T`.

## Deviation

The demotion covers exactly the two clause families the exercise reorders
(definitions and assignments); quote, if, lambda, and the rest keep their
typed dispatch, since the parser-level recognition stands in for the book's
pre-application clauses. The seam and the pinned faults are the exercise's.

## Answer

`(define x 3)` under `ApplicationsFirst` raises `Unbound("define")`;
`(set! x 3)` raises `Unbound("set!")`; a procedure definition is caught by
the application clause the same way. Under `CallSyntax`,
`(call (lambda (x) (* x x)) 7)` => 49, `(define (f x) x) (f 3)` => 3, and
`(twice (lambda (y) (* y 10)) 3)` with the call-prefixed body => 300.
