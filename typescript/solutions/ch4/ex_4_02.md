# Exercise 4.2: applications-first dispatch and the call-tagged evaluator

## Approach

Part (a) builds Louis's dispatch: the application clause moved in front of
assignment and definition. A definition is a pair, so `(define x 3)` is
taken for an application whose operator is the symbol `define`; evaluating
that operator looks the name up and fails. Part (b) builds the full
call-tagged dispatch of the dialect the book proposes: a procedure
application is a pair whose car is the symbol `call`, the operator is the
second element and the operands the rest, and there is no generic
application clause outside call.

## Numbers

With the ordinary evaluator, `(define x 3)` gives `ok` and `(+ x 1)` gives
`4`. With `evalApplicationsFirst`, `(define x 3)` fails with
`UnboundVariable` on the name `define`. With `evalCallTagged`,
`(call + 1 2)` is `3`, `(+ 1 2)` fails with `UnknownSyntax` naming the
expression `(+ 1 2)`, and `(call (lambda (x) (call * x x)) 7)` is `49`.

## Class and deviations

Translated row. Both dispatches are local re-assemblies; the module's
evaluator is untouched. The nested-body support of the call-tagged
dispatch mirrors the module's if, sequence, define, and apply helpers so
the recursion stays inside this evaluator; no other deviation.
