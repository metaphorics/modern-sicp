# Exercise 4.25: unless breaks under applicative order

## Approach

The same unless-based factorial runs under two evaluators. The lazy
experiment delays the arms at the call site, the condition forces only
the chosen arm, and the recursion bottoms out. The strict core keeps
the edition's strict-argument rule: every operand evaluates before the
procedure is entered, so the unused arm runs — its fault reaches the
caller before `unless` can choose — and the strict factorial descends
without ever reaching its base case. The descent runs against a host
budget on the recursive argument, so the predicted non-termination
answers as a typed budget error instead of hanging the run.

## Numbers

The lazy `unless` factorial answers `120`. Under the lazy experiment
the armed call answers `42` with the counter arm at `0`; under strict
arguments the same call answers `42` with the counter at `1`, and the
failing arm's `bad-operand` fault reaches the caller before `unless`
runs. The strict factorial answers
`bad-operand: the step budget ran out: factorial is still descending`.

## Class and deviations

Translated row. Deviations: the book's division-by-zero arm cannot
fault in this guest — the numeric rules make `1 / 0` infinity — so the
armed failure is a failing arm primitive carrying the same lesson in a
typed fault category; and the book's "runs forever" is observed through
a budget on the descending argument rather than an actual hang, which
turns the divergence into an observable typed error. The behavior the
exercise asks about is unchanged.
