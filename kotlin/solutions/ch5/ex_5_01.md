# Exercise 5.1: the iterative factorial machine (design)

The map class is `T`. The statement asks for a register machine that
computes factorials by the iterative algorithm, drawn as data paths and
a controller. This edition draws both diagrams in the book's figure
notation and pins the design by running its hand transcription
(`factorialController` in `solutions/ch5/E5_01.kt`) on the section's
hand model, so the design that is drawn is the design that runs.

The registers are the state variables of the iteration: `n` (the
input), `product`, and `counter`, the last two started at 1 by
`(iter 1 1)`. Two buttons change data: `p<-c*p` writes the product of
`counter` and `product` back into `product`, and `c<-c+1` increments
`counter`. The test `>` compares `counter` against `n` and has no
output arrow: its value goes to the controller only.

Data paths (rectangles are registers, `(X)` marks an assignment button,
the trapezoid is an operation computing a value, the circle is a test,
and the triangle is the constant 1):

```
+-------+               +-----------+              +-----------+
|   n   |               |  product  |              |  counter  |
+-------+               +-----^-----+              +-----^-----+
    |                         |                        |
    |                         | (X)                    | (X)
    |                         | p<-c*p                 | c<-c+1
    |                         |                        |
    |                   .=========.              .=========.
    |                  /    ***    \            /    ***    \
    +-----------------(  *  *   *  )----------(  *  +   *  )---(1)
    |                  \    ***    /            \    ***    /
    |                   '========='              '========='
     (test >: no output;                       the + operation's
      its value feeds the                       inputs are counter
      controller's diamond)                     and the constant 1
```

The `*` trapezoid serves `p<-c*p` (inputs `counter` and `product`); the
`+` trapezoid serves `c<-c+1` (inputs `counter` and the constant 1).
The test circle `>` takes `counter` and `n`.

Controller (boxes push the named buttons, the diamond is the decision,
`start` and `fact-done` are the entry and stop):

```
        start
          |
          V
         / \  yes
+-------> > >--------> fact-done
|        \ /
|         | no
|         V
|    +---------+
|    | p<-c*p  |
|    +----+----+
|         |
|         V
|    +---------+
+----+ c<-c+1  |
     +---------+
```

In the combined register-machine language of 5.1.1 the buttons become
the two `assign` instructions and the diamond becomes
`(test (op >) (reg counter) (reg n))` followed by
`(branch (label fact-done))`: exactly the transcribed
`factorialController`, so what runs is what is drawn. One design note:
the section's worry about simultaneous replacement does not arise here,
because `product`'s new value reads `counter`, not itself, so no
temporary register is needed.

Method: the machine's answers are computed by the hand model of
`Handsim.kt`, which steps the transcribed controller (registers,
flag, pc) the way a reader steps the diagram. `factorialMachineRuns()`
answers `["1", "1", "120", "3628800"]` on n = 0, 1, 5, 10, pinned in
`E5_01Test`. n = 0 answers 1 because `counter > n` holds immediately,
which is `(iter 1 1)` answering 1 without a single multiplication.
