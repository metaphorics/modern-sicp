# Exercise 2.69: `successive-merge` and `generate-huffman-tree`

## Approach

`successive_merge` repeatedly takes the two smallest-weight trees from
the front of the weight-ordered set (kept sorted by
`adjoin_huffman_set`), merges them with `make_code_tree`, and
re-inserts the merged tree, until one tree remains.
`generate_huffman_tree` is `successive_merge` applied to
`make_leaf_set`'s initial leaves. Run on `[(A, 4), (B, 2), (C, 1),
(D, 1)]`, the least-frequent pair `(C, 1)` and `(D, 1)` merges first,
producing the same leaf depths as the book's hand-built `sample-tree`.
Encoding `[A, D, A, B, B, C]` against the generated tree takes exactly
12 bits, matching `sample-message`'s length, and decoding those bits
reproduces the original message.

## Map class

`T`: translates directly onto the section library's `make_leaf_set`
and `adjoin_huffman_set`.

## Deviation

The exercise's expected result checks the generated tree's own
round trip and total code length rather than an exact bit-for-bit
match with `sample-tree`'s fixed encoding: the book's own footnote on
`make-code-tree` calls the left/right choice for a weight tie
arbitrary, and this generator breaks the tied `C`/`D` merge the
opposite way `sample-tree` was hand-written, which is a legitimate
Huffman tree with the same code lengths, not a bug.
