## Exercise 3.17: counting distinct pairs with a hand-rolled identity set

Approach: `countDistinctPairs` keeps Ben's traversal but remembers: the
`seen` list holds every pair on its first visit, and the `else if` at
the top of `walk` returns 0 for any pair already in it. Counting the
*first* visit only is what turns Ben's visit-count into a pair-count.

Why the auxiliary structure is a scanned list: the book's hint says to
maintain a structure of already-counted pairs, and membership there is
identity, not equality. Kotlin's `HashSet`/`MutableSet` key on
`equals`/`hashCode`, and `VPair.equals` is identity already -- but two
distinct pairs holding equal content must still be counted twice, so a
content-hashed set would be wrong for a `Value`-keyed variant, and the
runtime's contract ("`equals` is the book's `eq?`") is easy to defeat by
accident with a refactor. Scanning a `MutableList` with `===` states the
requirement -- identity membership -- directly in the code, which is
why this edition's statement points the reader there.

What the tests say: all three of exercise 3.16's structures -- the
chain, the count-4 sharing, and the count-7 double-sharing -- now
answer 3, and so does `cons(x, x)`, which has three physical pairs.
The third test calls the function twice on the same structure to pin
that `seen` is local to a traversal, not shared state. A version that
still double-counts fails the first test; a version that remembers
across calls fails the third.

Class: A (the host differs: Scheme solutions typically reach for an
`eq?`-hash table, while this edition's statement has the reader scan
for identity with `===`; the traversal itself is the book's).

Deviation: none.
