## Exercise 1.20: counting remainder calls under eager evaluation

Approach: a local `remainder` increments a closure-captured counter
before computing `a % b`, and a local `gcd` calls it exactly as the
section's `gcd` does. Reducing `gcd(206, 40)` eagerly takes four steps:
`remainder(206, 40) = 6` gives `gcd(40, 6)`; `remainder(40, 6) = 4` gives
`gcd(6, 4)`; `remainder(6, 4) = 2` gives `gcd(4, 2)`; `remainder(4, 2) = 0`
gives `gcd(2, 0)`, whose `b = 0` returns `2` with no further call. Four
calls to `remainder` in total.

Class: R (replace); this edition's signpost names the reason. SICP's own
exercise asks for the same count twice: once under Kotlin's only
evaluation order (applicative, matching the four calls just traced) and
once under normal order, where the substitution model defers every
`remainder` call until its value is forced by an `=` test, running the
same four productive calls plus a great many redundant ones (the book's
own answer is 18 total remainder calls under normal order for this
pair). Kotlin has no normal-order evaluation to run that second count
against; the material this exercise teaches (that an evaluation
strategy which resubstitutes unevaluated expressions can multiply the
number of primitive operations actually performed, here roughly 4.5
times over) survives as a fact stated in prose, since no Kotlin program
can be run to produce it.
