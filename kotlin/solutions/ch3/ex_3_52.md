# Exercise 3.52: accum traces assignment plus laziness

## Approach

`AccumProbe` carries the book's `sum` as a `var` plus an event log, one
entry per `accum` call, so the test sees both the running total and when
the pipeline ran each call. The test performs the book's script on the
memoized regime: the define of `seq` runs `accum(1)` and sum reads 1;
the define of `y` scans for the first even cell and sum reads 6; the
define of `z` scans for the first multiple of 5 and sum reads 10;
`streamRef(y, 7)` returns 136 and sum reads 136; the display of `z`
prints 10, 15, 45, 55, 105, 120, 190, 210 and sum ends at 210. The last
question gets a mechanical answer: `coldAccumScript` reruns the same
script over a delay without the memoized tail, where every force
re-derives its cells and re-runs `accum` over each cell it scans. The
responses change wholesale: the even filter collects 6, 24, 30, 54, 64,
100, 114, 162, 180; the five filter collects 15, 230, 245, 275, 300,
345, 380; sum ends at 419. The python3 mirror in the section check
replays both walks with the same operation order.

## Map class

`A` (map row 3.52: var sum plus lazy timing; the statement demands the
observable timing, and the probe provides it).

## Deviation

Two. First, several published answers report sum 190 after
`(stream-ref y 7)`; they drop the value 10 from `y`, but 10 is even, so
`y` is 6, 10, 28, 36, 66, 78, 120, 136, 190, 210 and the eighth element
is 136, leaving sum at 136: the Kotlin run and the python3 mirror
agree. Second, the counterfactual's exact numbers are this edition's own
derivation: the book only asks whether the responses would differ, and
the cold walk supplies the differences mechanically (final sum 419,
where the sweeps pass through the 220 to 420 band).
