# Exercise 4.24: analyzed versus direct, measured (adapt)

The map class is `A`: the experiment is carried out on this edition's
base evaluator, timed with `Sys.time` CPU milliseconds and no Unix
dependency. The pinned setup: the program is
`(define (fib n) (if (< n 2) n (+ (fib (- n 1)) (fib (- n 2)))))`, the
call is `(fib 11)` (287 procedure calls), `iterations` is 150, the
median is taken over 5 measured run pairs, and each side warms up over
one untimed run of the loop. The direct side evaluates the call per
iteration; the analyzed side analyzes it once, outside every timed
region, and runs the execution procedure per iteration. Each side
defines `fib` through its own evaluator in its own fresh environment,
because an analyzed `apply` runs only bodies its own `analyze`
registered.

The measured medians put the two evaluators within noise of each other
(repeated runs: direct ≈ 58–76 ms, analyzed ≈ 58–82 ms, ratios 0.9 to
1.1; one reference run answers 59.7 and 58.2). The reason is structural:
the typed AST reduces the direct evaluator's per-node dispatch to a
one-tag `Ast.view`, so analysis hoists almost nothing the direct
evaluator still pays for, and the shared costs (`Ok` boxing at every
step, frame allocation, primitive dispatch) dominate both. Analysis
itself measures at a few hundredths of a microsecond per call against
roughly 400 microseconds of execution per iteration, a negligible
fraction of the run; the analyzed evaluator's advantage in this edition
is architectural (dispatch decided once), not wall-clock.

Sample: `ex_4_24 ()` answers, for the reference run,
`["direct median: 59.7 ms"; "analyzed median: 58.2 ms"; "analyzed wins
by 1.0x"]`: the milliseconds are the reference host's; the format is
the contract.
