# Exercise 4.62 — last-pair rules (translate)

Two rules, as the statement suggests: the base case "the last pair of a
one-element list is that list" and the step "strip the first element". The
four statement queries behave differently, and the solution reports each as
the engine actually answers it:

- `(last-pair (3) ?x)` and `(last-pair (1 2 3) ?x)` answer once and run dry:
  the step rule's body walks down to `()`, where no rule matches.
- `(last-pair (2 ?x) (3))` terminates with exactly the intended answer. The
  step rule binds its tail variable to the query's structured one-element
  tail; re-applying the step rule to that body would unify the conclusion's
  `(?v . ?w)` with the already-bound tail — the `?v` step succeeds against
  the inner variable, but the `?w` step then requires the bound one-element
  list to unify with `()`, which fails, so the recursive branch dies after
  the one answer.
- `(last-pair ?x (3))` — the statement's real target — does not run dry:
  `?x` is free, so every application of the step rule rebinds its fresh tail
  variable and yields one more answer one level deeper, forever. The full
  query never terminates; the demonstration pins the finite prefix through
  `Eval.query_upto`, and the spurious answers carry the renamed rule
  variables the driver prints as `?name-<id>` (ids 20 and 22 under this
  demo's application sequence).

Deliberate deviation: none in the rules; the reverse queries are observed
through `query_upto` instead of forcing the whole stream, and the termination
facts are pinned as notes.

Asserted answers, verbatim (one string per element of `ex_4_62 ()`):

```

(last-pair (3) (3))

query: (last-pair ?x (3))
note: the full query never terminates; each step-rule application rebinds its fresh tail variable and yields one more answer; first three answers:
(last-pair (3) (3))
(last-pair (?v-20 3) (3))

```
