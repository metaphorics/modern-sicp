## Exercise 3.33: the averager as a three-constraint network

Approach: `averager` in `E3_33.kt` builds the standard three-box network.
`adder` pins a fresh connector `u` to a + b, a `constant` box pins a fresh
connector `v` to 2, and `multiplier(c, v, u)` pins `u` to c * v. The
multiplier is the only box that ever divides: its backward branch computes
`u / v`, so `c` comes out as (a + b) / 2 whenever any two of the three
connectors are given values.

Why (halving through the multiplier, not a division primitive): the exercise
allows only multiplier, adder, and constant, so the constant 2 is what turns
a multiplier into a divider. One consequence of the edition's `Long` values
has to be designed around: `total / x` in the multiplier truncates, so the
network halves exactly when a + b is even. The tests feed it 10 and 20 (and
drive it backward with c = 9, a = 8), all exact; a separate test feeds 7 and
10 and pins the truncation to 8, because that is what the device really
computes and a reader should see it stated, not surprised by it. Using
`Double` connectors would have traded this honesty for rounding noise
everywhere else.

What the tests say: `E3_33Test.kt` runs the average forward (a = 10,
b = 20 gives c = 15), runs it backward (c = 9 and a = 8 give b = 10, the
third inference direction this network owns), checks what forgetting `a`
retracts -- the adder-derived `u` and `c` fall, while `b` keeps the value
its own informant, the user, set (the book's "only those values that were
set by this adder are actually lost"), and `v` stays pinned at 2 -- and
pins the odd-sum truncation. A plausible bug -- say, an adder branch
ordering that infers from the wrong pair -- fails the backward test,
because that direction is the one that depends on the multiplier and adder
cooperating in sequence.

Class: `T` (the constraint builds and behaves in Kotlin as in the book; only
the halving-exactness caveat is host-language truth).

Deviation: none beyond the documented Long caveat.
