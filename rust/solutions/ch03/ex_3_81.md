# Exercise 3.81: rand request stream, no assignment

## Approach

The generator is a fold over the request stream carrying one word of
state. One fold step reads the request at the head: `Generate` answers
`rand-update` of the state and makes the answer the new state;
`Reset(n)` answers `n` itself and makes `n` the new state; the answer
is consed in front of the same fold over the requests' tail. The
"current word" of the 3.1-style generator exists nowhere as a mutable
cell -- it is only the argument each recursive call hands the next --
so the answer stream is a mathematical function of the request stream,
which is exactly what makes the tests honest: running the same request
list twice answers element-identical streams, checked by walking two
prefixes of two runs over one shared request stream. The mixed script
`generate, generate, reset 7, generate` pins the hand values of the
seeded chain: `rand-update(1)` = 5180492295206395165,
`rand-update` of that = 2586950713725923525, then 7 itself, then
`rand-update(7)` = 15130880334998875822. The determinism test ties the
formulation back to 3.5.5: the all-generate request stream from
`random-init` answers exactly `rand-update` mapped over the book's
`random-numbers` -- the same function grown from the same seed, one
self-reference versus one fold.

## Map class

`T`. The statement translates whole: a stream of requests answered by
a stream of words, no assignment. The Rust wrinkles: the book's
`generate`/`reset` symbols become a `RandRequest` enum (`Generate`,
`Reset(u64)`), and the fold consumes an endless request stream -- an
empty one has no request to answer, which the book's own generator
(which consumes an endless experiment stream) mirrors; the panic is
documented at the entry point.

## Deviation

None. The reset semantics are exercise 3.6's verbatim, and the seed
is the edition's fixed `random-init`.
