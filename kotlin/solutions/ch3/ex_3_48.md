# Exercise 3.48: deadlock avoidance by lock ordering

## Approach

Why ordering works: the serialized-exchange holds one serializer while
waiting for the other, so a deadlock needs two processes each holding
the other's waiting target. If every process acquires the
lower-numbered account's serializer first, there is always a
lowest-numbered account among the contended ones whose serializer some
process holds without wanting a second, and that process finishes; by
induction no cycle can close. The solution gives accounts a number
(`makeNumberedAccount`) and rewrites the exchange to order the two
wraps by number. The test runs opposing exchanges -- the book's
deadlock scenario -- concurrently and asserts both complete with the
multiset preserved, then runs the unordered pair with the switch points
forced by yields and asserts the timeout that proves the deadlock.

## Map class

`T`. The explanation and the rewrite are the statement's own.
