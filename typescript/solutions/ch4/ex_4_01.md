# Exercise 4.1: the two evaluation orders of list-of-values

## Approach

The book asks for both orders because Lisp leaves operand evaluation
unspecified. This host does not: the guest grammar evaluates call
arguments left to right, so the engine's `listOfValues` is already the
book's no-defer left-to-right version. The exercise is reworded
accordingly: instead of asking which order the language will take, it
states the host's order and asks for both book-faithful variants,
`listOfValuesLr` and `listOfValuesRl`, written over the typed operand
syntax with explicit recursion and no map, and pins the engine's version
against them. Operand order is observable in two ways: a session
transcript, because both variants evaluate operands through one `Session`
whose `console.log` output is collected in order, and shared guest state,
the `recorded` array the admitted recorder appends to.

## Numbers

Left to right over `rec("a")`, `rec("b")`, `rec("c")`: the transcript is
`["a", "b", "c"]` and the argument list is `["a", "b", "c"]`. Right to
left: the transcript is `["c", "b", "a"]` and the argument list is still
`["a", "b", "c"]`. The engine's `listOfValues` leaves the guest `recorded`
array as `["a", "b", "c"]`, matching `listOfValuesLr` operand for operand.

## Class and deviations

Adapted row: the premise is reworded. The book leaves the order open; this
edition states the guest grammar's left-to-right order and pins the engine
against the two variants. Both variants translate the book's code
directly; the optional `Session` parameter is the observation hook that
makes effect order visible in one transcript, and no other deviation.
