# Exercise 5.6: the redundant save and restore

The map class is `T`. Ben's extra pair in the Figure 5.12 controller is
the `(restore continue)` at `afterfib-n-1` and the `(save continue)` in
the second call's setup. Removed together, the controller of
`fib_modified_controller` in `solutions/ch5/sec_5_06.ml` keeps the same
answers.

Why this pair: each recursion level needs its caller's return address
exactly once, never twice. It is pushed once (before the first call), and
the only reader is the `(restore continue)` at `afterfib-n-2` after the
second call. The original controller carries that value twice: the
first push is popped by `afterfib-n-1`'s restore (which lands it in a
register the second call's setup immediately clobbers), and the second
push re-files the same value for `afterfib-n-2`. Deleting
`afterfib-n-1`'s restore and the second call's save leaves the value on
the stack across the whole level, pushed once and popped once.

The tempting alternative (deleting the second call's save and the
`afterfib-n-2` restore, keeping the middle restore) is wrong, and the
simulation says so: without the re-push, `afterfib-n-2`'s
`(restore continue)` would pop some ancestor's frame, and with it
deleted the level ends with `continue` still holding `afterfib-n-2`,
whose `(goto (reg continue))` then loops forever.

Evidence pinned by `ex_5_06 ()`, which answers
`["55"; "55"; "steps=281 saves=48"; "steps=257 saves=36"]`: both
machines on fib 10 answer 55, and the hand model's counts on fib 6
show the tree's twelve internal calls each shedding one save and one
restore: 48 saves become 36, and 281 executed instructions become 257.
The test suite also runs both machines over n = 0 through 9 and
pins the answers equal.
