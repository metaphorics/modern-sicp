# Exercise 3.26: a binary-tree table

## Approach

The book notes the chain-of-records table searches by scanning, the
unordered list of 2.3.3, and asks for records organized as a binary
tree instead, so `lookup` and `insert!` descend one `compare`-ordered
path. The edition renders the book's tree of mutable pairs as
`TreeEntry` records with mutable `left`/`right` fields (null for the
empty branch), the section's spelling of `set-car!`/`set-cdr!`. Each
record knows whether it holds the value stored under its key
(`isValueEntry`), because an insert created on the way down to a
deeper key exists as spine before it ever carries a value, exactly the
partial-path situation of 3.25 generalized to ordered keys. Insert
walks from the root and either replaces an existing key's value in
place or conses the new record onto the empty branch it falls off of;
lookup answers only where the descent lands on a value entry. The
table takes the comparison as a parameter, so any ordered key type
works.

## Pins

Inserting 5, 2, 8, 1, 3 (out of order) leaves `keysInOrder()` equal to
`[1, 2, 3, 5, 8]`. Lookups answer 30, 50, 10 for keys 3, 5, 1; keys 4
and 9 answer `undefined`. Re-inserting key 2 with 99 replaces the
value in place and leaves the in-order listing `[1, 2, 3, 5, 8]`. A
spine-only path: after inserting only 5, `lookup(3)` answers
`undefined` and the listing is `[5]`. String keys ordered
lexicographically list as `["apple", "fig", "pear"]` and `fig` finds 3.

## Map class

`T: binary-tree table over the section's mutable records`.
